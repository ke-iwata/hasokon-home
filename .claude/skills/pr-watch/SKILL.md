# PRを見張る

自分が出したPRを**マージかクローズまで**見届けるための手順。

## いちばん大事なこと：毎回とり直す

**前回の読みを信じない。ティックのたびに GitHub から取り直す。**

2026-09-24〜25 に、6本のPRが11〜15時間止まった。毎時のチェックは生きていたのに、
すべて「レビューコメント：なし」「対応すべき点なし」と報告していた。実際には
4〜7件の指摘が付いていた。

原因は時刻を並べると分かる。

| PR | 自分の最後の行動 | 相手の指摘が届いた時刻 |
|---|---|---|
| #238 | 22:39:41 に返信 | 22:41:01（1分20秒後） |
| #245〜#247 | 00:17〜00:21 に起票 | 00:23〜00:26（2〜5分後） |
| #253 | 16:21 に push | 16:37〜16:39（16分後） |

**相手の指摘は、いつも「自分が最後に状態を読んだ直後」に届く。** 起票や push の直後に
状態をまとめると、その「0件」が固定された認識になり、あとのティックでも更新されない。

対策は2つ。

- **投稿・push の直後にまとめない。** まとめるなら、その5〜10分後にもう一度取り直してから
- **ティックごとに必ず再取得する。** 「さっき見たときは無かった」は根拠にならない

## 状態のとり方

コメントは3種類あり、別々のエンドポイントに入る。**3つとも見る。**

```bash
gh api "repos/ke-iwata/hasokon-home/issues/<N>/comments"   # 1. 通常のコメント
gh api "repos/ke-iwata/hasokon-home/pulls/<N>/reviews"     # 2. レビュー（承認・要修正の本文）
gh api "repos/ke-iwata/hasokon-home/pulls/<N>/comments"    # 3. 差分行に付いたコメント
```

このリポジトリでは実績上ほぼ 1 に入るが、2 と 3 を見ない理由にはならない。

CI・コンフリクトも毎回とり直す（`mergeable_state` は前の値が残りやすい）。

```bash
gh pr view <N> --json mergeStateStatus,statusCheckRollup,commits,comments,reviews
```

「最後に動いた時刻」は **`updated_at` を使わない**。自動コメントでも動いてしまう。
コミット・`github-actions[bot]` 以外のコメント・レビューの最新時刻を使う。

## 次は誰の番か

- 最後のイベントが**相手の指摘** → **自分の番**。直すか、直せない理由をPRに書く
- 最後のイベントが**自分の対応** → 相手の番。待ってよい
- **PRがopenで、最後のイベントが自分のものでないなら、それは「待ち」ではない**

## 止めていい条件

**`merged` か `closed` になったときだけ。**

「やることが見つからない」は止める理由にならない。上の6本はすべてこの形で止まった。
対応すべき点が無いように見えるなら、それは前提の読み方を間違えている可能性が高いので、
まず取り直す。それでも本当に無ければ、**何を見て「無い」と判断したかをPRにコメントで残す**。
運営者の判断待ちなら、それも書いて止まる（これは正当な停止）。

## 長引いたとき

マージまで数日かかるとコンテキストを食う（実例：279.8k / 1M = 28%）。
ティックごとの記録は短く保つ。PRの状態はGitHubが持っているので、
セッション側で履歴を抱え込まない。
