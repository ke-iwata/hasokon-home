## 2026-08-21：ふるさと納税に令和8年対応の控除上限額 早見表を足した

仕様は [features/furusato-nozei-hayamihyo.md](../../docs/features/furusato-nozei-hayamihyo.md)。
既存の `/tools/furusato-nozei/` への追記で、新しいページは作っていない。

**一番の理由はSEOではなく「計算機に数字を入れる前に規模感を知りたい人」への回答。**
計算式の解説と計算機しかなく、「表を引きたい」層を受け止められていなかった。
FAQで「世間の早見表は社会保険料15%仮定で不正確」と指摘しながら自前の表を持っていない
ねじれも解消している。

**表の数値は手書きせず `calcFurusato` から生成する**（`hayamihyo()`）。年収300万〜1,500万
（800万までは50万円刻み、以降100万円刻み）× 家族構成4列。同じページの計算機と
食い違わせないためで、`shuzei-kaisei` の早見表と同じ方式。令和8年分の基礎控除・
給与所得控除の改正がロジック側に入っているので、**「2026年対応の早見表」であること自体が
差別化になる**（世間の早見表の多くは令和7年以前の前提のまま。500万円・独身で
約61,000円→57,000円と差が出る）。

**表示の丸めは千円未満の切り捨てに固定した。** 早見表はスクリーンショットで持ち帰られるので、
計算機の上限額を1円でも超える数字を載せると、その差がそのまま利用者の自己負担増になる。
**テストは一致ではなく「セル値 ≦ 同条件の `calcFurusato` の上限額」の不等式**で担保していて、
丸め単位を変えても生き続ける。

同じ理屈をセル自身にも効かせた。年収300万・夫婦＋子2人は上限額が自己負担と同じ2,000円まで
落ちる（住民税所得割額が1,950円しかない）。表の下の注記でカバーしても、**表は注記から
切り離されて持ち帰られる**ので、`hayamihyoNoBenefit()` で判定してセルに
「（実質的な効果なし）」を添えている。

**title を実測実績のある文字列から書き換えたので、撤退条件を残す。**
`ふるさと納税 控除額計算機｜上限額と所得税・住民税の内訳`（28字）→
`ふるさと納税 控除額の計算機・上限額早見表｜令和8年分`（27字）。Search Console で
表示が付いている「控除額」（3imp）を残し、実績のない「所得税・住民税の内訳」を落として
「上限額早見表」「令和8年分」を入れた。**公開4週間後に Search Console で「控除額」
「シミュレーション」系クエリの掲載順位を確認し、悪化していたら現行 title に戻す。**
書き換えの判断は根拠と撤退条件がセットで残っていないと4週間後に検証できない。

レビューで「40〜64歳は介護保険料のぶん**数千円**下がる」という注記が実測と合わないと
指摘され、直した（実測は年収300万で約570円・1,500万で約4,300円。300〜700万円帯では
数百円〜1,600円程度）。**元は仕様書の文言をそのまま写したもので、仕様書側も直してある。**
他所より正確なことが売りのページで幅を盛るのは自己矛盾になる。

## 2026-08-21：インボイス 納税額 比較計算機を追加した（公開前）

仕様は [features/invoice-2wari-tokurei-shuryo.md](../../docs/features/invoice-2wari-tokurei-shuryo.md)。
2割特例は個人事業者だと2026年分が最後で、2027年からは3割特例・簡易課税・本則課税の
どれかを選ぶことになる。売上高と業種を入れて4方式を並べる計算機。
`stage: 'preview'` で入れてある（公開の判断は運営者）。

**着手の前に一次確認を済ませた。** 仕様書は「令和8年度税制改正の後継措置は
税理士事務所の解説が複数一致するだけで一次資料未確認」という状態で起票されていて、
確認が取れないまま実装に流れ込ませない約束になっていた。国税庁の
「インボイス制度に関する令和8年度税制改正について」（令和8年4月）と
インボイスQ&A 問115-2・問117・問117-3 で全項目を確定させ、
結果を仕様書に書いてからコードを書いている。**3点とも解説どおりだった**
（3割特例の創設・7・5・3割控除・届出期限の特則）。

**差別化の中心は納税額ではなく届出期限。** 簡易課税の届出期限は原則が
「適用したい課税期間の初日の前日」＝個人なら前年12月31日で、これだけを見た人は
年が明けた時点で「もう手遅れ」と諦める。実際には2割特例・3割特例からの移行に特則があり、
**翌課税期間に係る確定申告期限まで**間に合う（28年改正法附則51の2⑥・51の3⑤）。
2027年分から簡易課税にするなら2026年12月31日ではなく**2028年3月31日**まで。
`kaniDeadline()` が原則と特則を必ず両方返す形にして、片方だけ出せない構造にした。

**「一番安い」を「一番いい」に見せない。** 納税額だけで並べると事務負担の重い
本則課税に誘導してしまうので、簡易課税の2年縛り・本則の帳簿保存・還付が出るのは
本則だけ、を結果の直下に固定で出している（`TRADE_OFFS`）。

**割合の引き算で1円ずれた。** `1 - 0.8` が 0.19999… になり、売上税額50万円の
第2種で納税額が99,999円になった。第3種（70%）と3割特例の同率比較も壊れていた。
`roundRate()` を通す形に直してテストで固定した。第3種は3割特例と「同じ」であって
「安い」ではない——ここを丸めると誤案内になる。

**レビューで「2026年分を選ぶとページごと落ちる」が見つかった。** `specialFor()` を
`YEARS`（＝画面の選択肢の表）のルックアップで書いていたため、`kaniDeadline()` が
**前年**を尋ねた瞬間に選択肢の外（2025年）へ出て throw していた。
届出期限の判定が前年を見るのは当たり前の操作なので、`specialFor()` は
**制度の年そのものから答える純関数**に直し、`YearDef` から `special` を消して
情報源を1つにした。テストは個別の年ではなく **`YEARS` を回す不変条件**にしてある
（行を足したときに同じ穴が空かないように）。落ちていたのが
**このページの主題そのものの年**で、届出期限パネルの価値がいちばん高いところ
（2025年分に2割特例を使った人は、原則の2025年12月31日を過ぎていても
特則で2027年3月31日まで間に合う）だったのが痛い。修正後は Chromium で
4つの年をすべて切り替えて、ページエラー0件・期限の表示・390pxの溢れなしを確認した。

## 2026-08-19：画像リサイズ・圧縮を追加した（完全ローカル生成系の3本目・公開前）

仕様は [features/gazo-resize-asshuku.md](../../docs/features/gazo-resize-asshuku.md)。
QRコード作成・パスワード生成で確立した「ブラウザ内で完結・どこにも送信しない」路線の
3本目で、当サイト初の画像系。`stage: 'preview'` で入れてある（公開の判断は運営者）。

**Canvas で描き直す構成そのものが差別化になる。** 主要な競合はファイルをサーバーへ
送って処理するので、履歴書の証明写真・免許証の写し・子どもの写真といった
「送りたくない画像ほどリサイズが必要」な場面で不安が残る。ここは
`createImageBitmap` → Canvas → `toBlob` だけで組んであり、送信する処理が存在しない。
外部ライブラリも使っていない（HEIC 対応の wasm デコーダは MB 級になるので初版では見送り。
トリミング・回転・文字入れも入れない）。

**EXIF は「消す機能」ではなく、描き直した結果として消える。** 位置情報・撮影日時・
機種情報は Canvas 経由で引き継がれない。ただし**向き（Orientation）だけは消えると困る**
——スマホの縦撮りは画素としては横向きに保存されていて「EXIF を見て回してね」という
作りなので、向きを無視して描くと横倒しになる。そこで `readExifOrientation()` で APP1 の
TIFF を辿って向きを読んでいる。

**ただし「自分で回す」かどうかは、ブラウザの実挙動を測ってから決める。**
`createImageBitmap(blob, { imageOrientation: 'none' })` は仕様上「EXIF を反映しない
生の画素」を返すはずだが、**Chromium はこの指定を無視して常に反映した状態で返す**
（141.0.7390.37 で実測。[whatwg/html#7210](https://github.com/whatwg/html/issues/7210)）。
反映済みの画像にこちらでも回転を掛けると**二重補正**になり、向き6の写真は90度余計に
回り、向き3では打ち消し合って補正が効かなくなる。オプションの意味は当てにならないので、
**判定用の極小JPEG（画素2×1・Orientation=6）を1枚だけ復号して、縦長で返ってくるか**で
そのブラウザの挙動を実測し（`ORIENTATION_PROBE_JPEG_BASE64`）、反映しないブラウザで
だけ自分で回す（`orientationToApply()` / `visibleSize()`）。「元のサイズ」の表示も
同じ判定を通す（反映済みの寸法をさらに読み替えると、縦写真に横のpx値が出る）。

この不整合は**純関数のテストでは捕まらない**（jsdom に `createImageBitmap` の実装が
無い）。判定と読み替えの規則そのものは単体テストで固定したうえで、実ブラウザ
（Playwright + Chromium）でビルド済みページを開き、向き1・3・6・8 のJPEGについて
**ブラウザが `<img>` で表示する向きとツールの出力の向きが画素レベルで一致すること**を
確かめている。ブラウザ依存の箇所は、この形で確かめてから入れること。

**ブラウザ依存の部分を持ち込まないよう、純関数を4つに絞って `lib/gazo-resize.ts` に置いた。**
Canvas の描画結果はテストで固定できないので、テスト（`tests/gazo-resize.test.ts`・43件）は
この4つに掛けている。

- `computeTargetSize()` … 幅・高さ／パーセント／長辺の3モードの寸法。既定で
  **比率固定・拡大なし**（引き伸ばしても情報は増えないため）。指定が足りないときは
  `null` を返す。ここで元サイズに化けさせると「リサイズされていない」ことに気づけない
- `downscaleSteps()` … 多段縮小の刻み。一度に大きく縮めるとジャギー・モアレが出るので
  半分ずつ寄せてから目標サイズに合わせる
- `searchQualityForTargetSize()` … 「300KB以下」を満たす**いちばん高い品質**の二分探索。
  エンコードは呼び出し側（`canvas.toBlob`）に注入する形にして、テストでは
  品質に対して単調なダミーで収束条件を固定した。**下限品質でも届かないときは
  `reached: false` を返して画面で伝える**（勝手に寸法を縮めない）
- `readExifOrientation()` / `orientationTransform()` … 向きの読み取りと、回転・反転への読み替え。
  JPEG のマーカーを組み立てたバイト列でテストしている（II / MM の両方）

WebP を書き出せないブラウザは `toBlob` が黙って PNG を返すので、結果の `blob.type` を
見て実際の形式を表示している。複数枚は1枚ずつ順に処理する（大きな写真を同時に展開すると
端末のメモリを使い切るため）。ZIP にまとめないのも同じ理由で、圧縮ライブラリを
読み込むぶんページが重くなるのは避けた。

## 2026-08-19：失業保険（基本手当）計算機を追加した（令和8年8月1日改定・公開前）

仕様は [features/shitsugyo-hoken-kihon-teate.md](../../docs/features/shitsugyo-hoken-kihon-teate.md)。
`stage: 'preview'` で入れてある（公開の判断は運営者）。社会保険クラスタに
「辞めたらいくら」の受け皿がまだ1本も無かった枠を埋めるもので、傷病手当金（病気で休む）と対になる。

**給付率は「およそ50〜80%」と丸めず、法定の算式をそのまま実装した。** 厚労省
「基本手当日額の計算式及び金額(令和8年8月1日～)」の
`y = 0.8w − 0.3{(w − 5,480)/(13,490 − 5,480)}w` を数式のまま持たせ、屈折点・上限下限・
1円未満切り捨てをテストで固定している。率を丸めると逓減帯の真ん中が最大で数百円ずれる。
**60〜64歳だけは逓減帯に算式が2本あり、低いほうを採る**（`y = 0.05w + 12,120×0.4`）。
片方だけ実装すると賃金日額9,000円あたりで200円ほど過大に出る。

**給付制限は「原則2ヶ月」ではなく原則1ヶ月。** 令和7年4月1日以降の離職について短縮された。
古い数字のままの解説記事が多いので、画面と解説の両方で独立した見出しにしてある。
5年内に2回以上の自己都合離職（今回は数に入れない）と重責解雇は3ヶ月。
**教育訓練等による解除は重責解雇には効かない**（一次情報の注2）ので、`restrictionFor()` は
重責解雇を教育訓練の判定より先に返している。ここを一律解除にすると、3ヶ月の空白がある人に
「待期のあとすぐもらえる」と表示してしまう。

**差別化の柱はスケジュール。** 待期7日・給付制限・支給対象の開始日・所定給付日数を
使い切る日を暦日で出し、**受給期間（離職日の翌日から1年）に収まるか**まで判定する
（`Schedule.fitsInEligibility`）。給付制限3ヶ月＋330日のような組み合わせは1年に収まらず、
「もらえるはずの日数」と「実際にもらえる日数」がずれる。金額だけ出す競合はここを出していない。
日付は `lib/date-parts.ts` を使い回した（応当日が無い月は末日に寄せる扱いもそのまま効く）。

**表に「―」しかない組み合わせ（30歳未満 × 加入20年以上など）は0日を返さない。**
画面からは選べてしまうが、0日と出すと「1円ももらえない」と誤読される。日数のある区分まで
下げて引き、`PrescribedDaysResult.adjusted` で断る形にした。

**受給資格の被保険者期間（12ヶ月か6ヶ月か）は、`category` にも `reason` にも寄せられない。**
所定給付日数の表（`category`）・給付制限（`reason`）・受給資格の要件は**3つとも独立した軸**で、
「正当な理由のある自己都合」は `category: 'ippan'`（一般の表）なのに6ヶ月で足り、
「定年退職・更新を希望しなかった契約満了」は `reason: 'company'`（給付制限なし）なのに
12ヶ月が要る。最初は `category === 'ippan'` だけで注意書きを出していて、
**特定理由離職者に「受給資格がない」と読める表示をしていた**（レビューで指摘されて修正）。
`KihonTeateInput.relaxedEligibility` を明示的に受け取る形にし、離職理由5種すべて ×
加入1年未満をテストで固定した。`insuredMonthsRequired()` の既定の推定は
「特定受給資格者だけ緩和」という控えめな側に倒してある。
## 2026-08-19：坪・平米・畳 変換を追加した（単位換算系の1本目・公開前）

仕様は [features/tsubo-heibei-jo-henkan.md](../../docs/features/tsubo-heibei-jo-henkan.md)。
アスペクト比計算・年齢早見表と同じ「数値つきロングテールを1ページの逆引き早見表で受ける」型で、
広さの単位換算に横展開したもの。`stage: 'preview'` で入れてある（公開の判断は運営者）。

**1坪 = 400/121㎡ を分数のまま持ち、丸めるのは表示のときだけにした。** 1尺 = 10/33m、
1間 = 6尺、1坪 = 1間四方から厳密に導ける値で、3.31 や 3.3058 で計算すると坪数が
大きいほど早見表と計算機がずれる。逆向きの 121/400 = 0.3025 は割り切れるので、
「100㎡ = 30.25坪」はちょうどになる。

**畳の寸法はミリメートルの整数で持っている。** メートルの小数で
1.70 × 0.85 を掛けると二進小数の誤差で 1.4449999… になり、団地間の1畳が
表示で1.44㎡に落ちた（実際は1.445㎡ → 1.45㎡）。寸法を mm の整数にして
最後に 1,000,000 で割り、`roundArea()` も指数表記の文字列を経由して
10進で四捨五入する形にしてある。この2点は
`tests/tsubo-heibei.test.ts` の「団地間の 1.445㎡ が 1.45㎡ に丸まる」で固定した。

**既定の畳は「不動産表示（1.62㎡）」にした。** 畳は京間 約1.82㎡・中京間 約1.66㎡・
江戸間 約1.55㎡・団地間 約1.445㎡と規格で違うが、利用者が見ているのはたいてい
不動産広告の「◯畳」で、これは不動産の表示に関する公正競争規約施行規則が
「畳1枚あたり1.62㎡以上」と定めた換算で書かれている。1.62㎡は江戸間・団地間より
大きいので、**実際に敷いてある畳の枚数より広告の畳数のほうが少なくなりうる**。

## 2026-08-18：パスワード生成を追加した（生成系の2本目・セキュリティ系の1本目・公開前）

仕様は [features/password-seisei.md](../../docs/features/password-seisei.md)。
QRコード作成で開いた「ブラウザ内で完結・データ送信なし」の路線の2本目で、
セキュリティ系ジャンルの1本目。`stage: 'preview'` で入れてある（公開の判断は運営者）。

**乱数の作り方を3つ固定した**（`tests/password.test.ts` が見張っている）。

1. `crypto.getRandomValues()` だけを使う（`Math.random()` は使わない）
2. **剰余バイアスを作らない。** `乱数 % 文字数` は割り切れないぶん先頭の文字が
   出やすくなるので、端を捨てて引き直す棄却サンプリングにした
   （0〜255を10で割ると0〜5が26回・6〜9が25回で4%ずれる。見た目では気づけない）
3. **文字種の保証は「引き直し」ではなく「先に確保してシャッフル」。**
   条件を満たすまで生成し直す方式は条件付きの分布になって偏る

**パスフレーズ用の単語リスト（2,048語）は完全自作。** EFF の Large Wordlist などを
転用・訳出していないので、ライセンス表記が要らず配布にも制約がない。
参考にしたのは「語数とエントロピーの関係」という公知の計算方法だけ。
**ちょうど2,048語（2^11）にしたのは1語を11ビットちょうどにするため**で、
語数を変えると画面とFAQの説明が半端になる。
品質は `tests/password-words.test.ts` が固定している（語数・重複・文字種・長さ・
「1文字違いの相手が4語以上ある語を入れない」）。ローマ字の日本語は
`kaki / kagi / kami` のように1文字違いが自然に生まれるためゼロにはできず、
できるのは紛らわしい語が1か所に集まるのを止めることだけ、という整理にした。

**パスフレーズの既定は6語（66ビット）。** 4語＝44ビットは、このツール自身の
目安表示で「弱い」に入る（毎秒1兆回で平均9秒）。既定値が自分の基準で弱いのはおかしい。

**生成は必ず `useEffect` の中で行う。** 静的書き出し（`output: 'export'`）なので、
描画中に乱数を引くとビルド時の値がHTMLに焼き付き、**全員に同じパスワードが配られる**。

解説は総務省「国民のためのサイバーセキュリティサイト」・IPA「チョコっとプラスパスワード」・
NIST SP 800-63B を一次情報として、長さ優先・使い回し禁止・定期変更の強制は不要、で揃えた。
やらないことは仕様書どおり**強度判定機（既存パスワードを入力させる機能）**で、
入力させないこと自体が信頼の設計。

**エンコーダを自前で実装した（外部ライブラリを使わない）。** このツールの差別化は
「入力内容が送信されない」「作ったQRに期限がない」の2点で、外部APIはもちろん、
外部ライブラリを足すのも依存を増やさない既存方針に反する。規格（ISO/IEC 18004）は
公開されていて基本特許も失効しているので、モデル2・バイトモード（UTF-8）・
誤り訂正レベルM/Q・版数1〜40に絞って `lib/qr-code.ts` に閉じた。

URLとWi-Fi設定という主な用途には効かない）。

**版数ごとの分割表は持たず、ブロック数と誤り訂正コード語数の2つの表から導いている。**
ブロックの長さは最大で1コード語しか違わないので、短いブロックの数から分け方が決まる。
40版×2レベルの分割表を書き写すより、写し間違いの入る余地が小さい。

**正しさの担保は4方向から。** QRは「少しずれた盤面でもそれらしく見える」ので、
目視では確かめられない。印刷して配られたあとに気づくことになるため、
`tests/qr-code.test.ts` に次を置いた（69件）。

- **規格の表との突き合わせ** — コード語数・容量・位置合わせパターンの座標
- **既知のベクタ** — リード・ソロモンが規格の計算例と一致すること
- **別実装との一致（ゴールデン）** — 実績のある実装（npm の qrcode）が出した盤面と
  1マスも違わないこと。**マスクは向こうが選んだ番号に固定して比べる**
- **盤面からの読み戻し** — テスト側で機能パターンの位置を独立に組み立て直し、
  埋め込んだコード語を復元できること

**マスクの選び方は実装ごとに差が出るが、揃えにいかない。** 規格の減点規則は
「シンボルの外側を明領域として数えるか」などの解釈に幅があり、実装によって
選ぶ番号が違う。どれを選んでも読み取りには影響しないため、ゴールデンでは
マスクを固定して盤面だけを比べている（実装は規格の4規則をそのまま書いている）。

**動的QR・短縮URL・アクセス解析はやらない。** サーバーが要るうえ、
「送信しない・期限がない」というこのツールの存在理由と正面から矛盾する。
解説とFAQでは、無料QR作成サイトの「期限切れ・転送」が動的QRの仕組みから来ることを
静的QRとの比較表で説明し、ここが検索面の本体になるようにした。

**ロゴ埋め込み・色変更などの装飾も入れていない。** まず読み取り確実性を優先する。
画面のダウンロードはPNG（512px）とSVGの2つで、印刷にはSVGを勧めている。

- **「含まない」の空白は全角スペース（U+3000）も除く**。日本語では字下げに
  全角スペースを使うため、1文字として残ると期待とずれる

**目標文字数の判定に使う数え方は利用者に選ばせた**（スペース・改行を含む／含まない）。
エントリーシートは「含まない」、小論文は「含む」で指定されることが多く、
どちらか一方を固定すると残り文字数が当てにならない。既定は「含む」。

**全角・半角の内訳は `hankaku-zenkaku.ts` の `countChars()` を再利用した。**
同じサイトで「全角何文字」の定義が2つあると説明できなくなる。
あわせて `countChars()` の判定に絵文字の範囲（U+1F300〜U+1FAFF）を足した。

及ぶのは子1人あたり月8万円までで、取り決めた養育費の全額ではない。どちらも
「改正で養育費が保障された」という粗い理解のまま読み飛ばされやすいので、
本文でもFAQでも別建てにしてある。

**免責は結果の直下に固定表示した。** ページ末尾に一度書くだけだと、金額を見て帰る人には
届かない。`.note` を金額パネルの中に入れて、目安であること・実際は協議／調停／審判で
決まることが必ず目に入るようにしている。

**算定表の範囲外では金額を出さない。** 年収が給与2,000万円・自営1,567万円を超える場合や
子が4人以上の場合、方式をそのまま延長した額が実務で通るとは限らない。理由だけを示して

リード獲得ページばかりなので、中立性を保つために相談誘導のリンクは置いていない。

**婚姻費用は扱わない。** 権利者本人の生活費も含むため別の算定表（表10〜表19）が必要で、
1ページ＝1ツールの原則からも別ツールの領域。

## 2026-08-15：日数計算・期日計算を追加した（24本目のツール）

恒常需要の非YMYLツールとして `tools/nissu-keisan/` を追加した。2つの日付のあいだの
日数（初日を含む・含まないの両方／週・月・年月日の内訳／曜日）と、「◯日後」「◯営業日後」の
期日計算を1ページにまとめている。仕様は
[features/nissu-keisan.md](../../docs/features/nissu-keisan.md)。

**祝日は式で導かず、内閣府の一覧を写した静的テーブルで持った。** 春分の日・秋分の日は
国立天文台の暦要項で確定し、翌年分が官報に公示されるのは毎年2月ごろ。近似式で先の年まで
埋めると、営業日計算が「それらしい答え」を返しながら静かに1日ずれる。テーブルの範囲
（`HOLIDAY_FIRST_YEAR`〜`HOLIDAY_LAST_YEAR`）を外れる日付を渡されたら、概算せずに
「祝日データの範囲外」と返して計算を断る。

**そのかわり、テストでは祝日法から独立に導出して突き合わせている。** 手写しは写し間違いが
入る。`tests/nissu-keisan.test.ts` がハッピーマンデー・振替休日（3条2項）・国民の休日
（3条3項）・春分秋分の近似式から各年の休日を組み立て、テーブルと1日単位で比較する。
導出はテスト側にしか置かない——libに置くと未公示の年まで埋まってしまい、上の判断が崩れるため。

**日付の基本操作は `lib/date-parts.ts` へ切り出した。** うるう年・月末の寄せ・日数の差・曜日は
年齢計算（`lib/nenrei.ts`）が既に持っていたが、日数計算からも同じものが要る。日数計算が
年齢計算に依存する形は読みにくいので共通の土台に移し、`lib/nenrei.ts` は同名で
再エクスポートして既存の利用側を触らずに済ませた。

**「◯日後」は起算日を数えない。** 民法140条の初日不算入にそろえた。営業日も同じで、
起算日の次の営業日が1営業日目になる。いっぽう日数計算のほうは初日を含む・含まないの
両方を並べて出す。契約の期限（初日不算入）と旅行の日程（初日を含む）で必要な数字が
違い、どちらか一方だけ出すと必ず取り違えが起きるため。

**「1か月後」は日数に換算しない。** 民法143条の応当日の考え方で数え、応当日が無い月は
末日に寄せる（1月31日の1か月後は平年2月28日・うるう年2月29日）。`addMonths()` が
この寄せを持っている。

**会社ごとの休業日は扱わない。** 年末年始・お盆・創立記念日は企業ごとに違い、正解が無い。
12月30日は営業日として数えることをFAQと画面の注記で明示した。金融機関の休業日
（12月31日〜1月3日）とも違う点も併記している。

## 2026-08-14：年齢計算・西暦和暦変換を追加した（23本目のツール）

恒常需要の非YMYLツールとして `tools/nenrei-keisan/` を追加した。生年月日から満年齢・
和暦表記・干支・誕生日までの日数・入学卒業年の目安を出し、明治〜令和の西暦⇔和暦
早見表も同じページに載せている。仕様は
[features/nenrei-keisan.md](../../docs/features/nenrei-keisan.md)。

**元号は「開始日・終了日」の組で持った。** 年だけで持つと改元年（1989年＝昭和64年と
平成元年、2019年＝平成31年と令和元年）を1つに丸めてしまう。`ERAS` に暦日の範囲を
持たせ、`toWareki()` は日付で元号を引く。早見表でも改元年は両方の元号に行が出て、
備考に「1月7日まで」「1月8日から」と入る。書類の記入で迷うのがまさにここなので、
重複を隠さないほうを選んだ。

**存在しない和暦は弾くだけにせず、理由を返した。** 「昭和64年1月8日」のような入力に対して
`fromWareki()` は `{ error }` を返し、「1989年1月8日から平成」と示す。単に無効と出すより、
正しい表記に辿り着ける。

**明治より前には対応しない。** グレゴリオ暦の採用は明治6年1月1日（1873-01-01）で、
それ以前の和暦の月日は旧暦なので西暦と機械的に対応しない。明治元年〜5年は年の対応だけを
示し、`WarekiDate.lunisolar` を立てて注記を出す。

**満年齢は誕生日の当日から新しい年齢にした。** 年齢計算ニ関スル法律＋民法143条では
誕生日の前日の終了時（24時）に増えるので、日付の比較としては当日で増えるのと一致する。
2月29日生まれは平年に応当日が無く、民法143条2項ただし書きで2月28日の終了時に満了するため、
**平年は3月1日に増える**（2月28日はまだ増えない）。`nextBirthday()` も同じ日へ寄せる。

**学年は「4月2日〜翌年4月1日生まれ」で1つのまとまりにした。** 学校教育法17条の
「満6歳に達した日の翌日以後における最初の学年の初め」と、前日満了の年齢の増え方を
合わせると、4月1日生まれは3月31日に6歳になってその年の4月に入学する。早生まれが
1月1日〜4月1日になる理由がここにあるので、FAQでも導出を書いた。

**早見表の現行元号は固定の上限年（`TABLE_END_YEAR`）まで出す。** ビルド時刻から作ると
ビルドのたびに行数が変わり、テストが不安定になる。表の末尾に近づいたら定数を伸ばす。

`lib/koko-jugyoryo.ts` / `app/koko-jugyoryo/` を追加し、2026年4月の

**理由**：所得制限が撤廃されて「もらえるか」の判定が不要になった一方、論点が

思ったより払う」というギャップが検索需要の中心にある。進路決定・出願は9月〜1月に
集中するので、いま出せば季節需要の立ち上がりに間に合う。

入力項目を増やしても結果が動かない。都道府県の上乗せ助成には所得要件が残る場合が
あるが、47都道府県のデータ化は更新負荷が高いので v1 では注記と外部リンクに留めた。

**仕様書の記述を一次情報で補正した点が2つある。**
仕様書は通信制を「1単位13,668円・年30単位・通算74単位」とだけ書いていたが、
文科省の令和8年度説明会資料（p.4 / p.24）で確かめたところ、
私立通信制には**定額授業料の場合の年33万7,200円**という別の限度額があり、
13,668円/単位は**単位制授業料を設定している学校**の額だった。ツールは単位制だけを
扱うことにし（通信制は単位制が主流のため）、定額制の33万7,200円は解説の表に載せた。

限度額より安い学校では授業料の額で止まり、差額が現金でもらえるわけではない。
`Math.min(限度額, 実際の授業料)` を必ず取っている。

通算74単位の上限は**在学年数をまたいで効く**ので、学年ごとに残り単位数を減らしながら
積んでいる。年30単位を3年続けると90単位になり、超過した16単位分は丸ごと自己負担になる。
黙って丸めず、頭打ちに当たったときは学年ごとの支給対象単位数を画面に出す
（`lib/shobyo-teate.ts` の通算1年6ヶ月と同じ考え方）。

「授業料以外の年間費用」の目安ボタン（公立15万円／私立30万円）は
**公式の統計値そのものではない**。子供の学習費調査の学習費総額から授業料と
学校外活動費を除いてならした概算なので、初期値には使わず（0を初期値にした）、
ボタンとしてだけ提示し、学校案内の「初年度納付金」で入れ替えてもらう建て付けにした。

## 2026-08-13：傷病手当金の支給対象日数に「通算1年6ヶ月」の上限を入れた

`lib/shobyo-teate.ts` に `MAX_PAYABLE_DAYS = 546` を置き、支給対象日数を
`min(休業日数 − 待期3日, 546)` で頭打ちにした。上限に達したときは結果パネルに
「入力の◯日分ではなく546日分で計算しました」と理由を出す（黙って丸めない）。
入力欄に `max` は付けない。2年休んだ人が「730」と入れるのは自然で、弾くと
「1年6ヶ月で切れる」という制度説明の機会そのものを失うため。

**理由**：ページ本文とFAQが「支給期間は通算1年6ヶ月」と2箇所で説明しているのに、
計算だけが上限を持たず青天井だった。月収30万円で730日と入れると4,846,909円と出るが、
制度上の上限は546日分の3,640,182円で、約120万円・33%の過大表示になっていた。
長期療養を想定して長い日数を入れる人ほど踏むので、いちばん切実に金額を知りたい層が
誤った額を見ることになる。仕様は
[docs/features/shobyo-teate-shikyu-kikan-cap.md](../../docs/features/shobyo-teate-shikyu-kikan-cap.md)。

546日は「1年6ヶ月」を暦で数えたときの実日数（546〜548日）のうち短いほうを採ったもの。
金額を調べる道具なので、多く出しすぎる側より過小に倒すほうが害が小さい。

## 2026-08-11：ルーレットの「配色」テーマ選択を廃止した

4種類（ポップ／パステル／ビビッド／あたたか）から選べたテーマを廃止し、
`lib/roulette/colors.ts` の固定セット（旧ポップの札10色 + 共有画像の代表色）に一本化した。
localStorage の `roulette:theme` は読まなくなっただけで、残っていても害はない。

**理由**：デザイントークン統一の際、テーマがページ全体の配色（--bg / --text 等）を

その時点でテーマの差は札の色だけになり、選択UIを残す価値が薄くなったので
運営者の判断で機能ごと外した。選択肢が減るぶん初見の画面も簡素になる。
