## 2026-08-13：社会保険 損得計算機の料率を令和8年度に直し、子ども・子育て支援金を入れた

`tools/lib/hatarakizon.ts` の `HEALTH_RATE` を 4.99%→4.95%（協会けんぽの全国平均9.9%の折半）、
`KAIGO_RATE` を 0.8%→0.81%（全国一律1.62%の折半）に更新し、
2026年4月に始まった子ども・子育て支援金（本人負担0.115%）を健康保険料に足した。
標準報酬月額30万円の健康保険料は 年179,640円 → 182,340円（40〜64歳は211,500円）になる。
仕様は [features/hatarakizon-r8-hokenryoritsu.md](./features/hatarakizon-r8-hokenryoritsu.md)。

**理由**：料率が5か月前の改定に追随しておらず、支援金は1円も引かれていなかった。
保険料を年2,700〜3,060円 少なく見積もる＝手取りを多く表示する向きのずれで、
「働き損の境目を1円単位で言い当てる」というこのツールの存在理由に直接効く
（損益分岐点が実際より低い年収に出ていた）。

**支援金率は `hatarakizon.ts` に持たず、`lib/kosodate-shienkin.ts` の `FISCAL_YEARS` から引いた。**
同じ数字を2か所に置いたことが今回の不整合そのものだったため。
`/tools/kosodate-shienkin/` が「月345円引かれます」と答えるのに
`/tools/hatarakizon/` がその345円を引かない、という食い違いが起きていた。
料率の更新は `FISCAL_YEARS` の1か所で済み、テストが両者の一致を見張る。

**仕様書は年度を `2026` で決め打ちする実装例を挙げていたが、`status === '確定'` の
最新年度を選ぶ形にした。** 決め打ちだと令和9年度の確定値が入ったときに
`hatarakizon` だけが取り残され、仕様書自身が期待効果に挙げた
「`FISCAL_YEARS` の更新だけで両ツールが追随すること」を満たせない。
`見込み`・`政府試算` は選ばないので、手取りは確定値だけで出すという方針は変わらない。

**支援金は内訳の独立した行にせず、健康保険料に含めて同じ端数処理に入れた。**
給与明細でも健康保険料と一体で徴収されるため。内訳を1行増やすと
ツールの主題（働き損の境目）から目が逸れる、という仕様書の判断に従った。

## 2026-08-13：ゲームに「麻雀ソリティア」を追加した（絵合わせの最初の1本）

`games/lib/mahjong-tiles.ts`（42種の絵柄と合わせ判定）・
`games/lib/mahjong-solitaire.ts`（亀レイアウト・選択可能判定・必ずクリアできる配り方・
詰み検出・並べ替え）・`games/app/mahjong-solitaire/`（画面と牌のSVG）・
`games/tests/mahjong-solitaire.test.ts`（46件）。
`games/lib/registry.ts` と `home/index.html` の一覧にも足した。
仕様は [features/game-mahjong-solitaire.md](./features/game-mahjong-solitaire.md)。

**理由**：既存9本はトランプ3・数字パズル3・アクション2・ボード1で、
「絵合わせ」が1本も無かった。タップ2回だけで完結するのでモバイルとPCで操作が同じになり、
検索表示の過半（103/197）を占めるモバイルからの流入を受け止められる。

名称は**麻雀ソリティア**にした。日本での通称「上海」はサン電子（サンソフト）が
国内で商標を保有しているため、`<title>`・`h1`・`registry.ts` の `name` には入れない。
リバーシで「オセロ」を避けたのと同じ判断。牌の意匠自体は伝統的なもので権利者がいないので、
42種すべて自前のSVGで描いた（筒子は円の配置、索子は竹の配置を表で持ち、
萬子・字牌・花牌・季節牌は文字を置く。絵文字を使わない理由は `app/GameIcon.tsx` と同じ）。

**「必ずクリアできる配置」は、仕様書の「逆再生で配る」を逆から書いて実装した。**
空の盤に積んでいくのではなく、**満杯の盤から2枚ずつ「選べる牌」を取り除く順番を先に作り**、
その組に同じ絵柄を割り当てている。牌を取り除いて他の牌が塞がることは無いので、
置ける位置を毎回探すより素直で、取り除ける順番がそのまま「必ず消せる順」になる。
テストは100回配ってそのすべてがこの順で全消しできることを見ている。
並べ替え（シャッフル）も同じ関数を場に残っているマスだけに通しているので、
**詰みで押したのに詰みのまま、が起きない。**

**仕様書から変えた点：枚数を136枚ではなく144枚にした。**
仕様書は本文で「136枚」と書きつつ、同じ仕様書が
「花牌（春夏秋冬）・季節牌は同じ組の中ならどれとでも合う」という伝統ルールと
「牌のSVG…花牌は4種」を求めている。花牌・季節牌を入れずに136枚にすると
このルールが実装対象を失い、亀（Turtle）レイアウト（144マス）にも8マス足りない。
**34種×4枚＝136枚という不変条件はそのまま守り、花牌4枚・季節牌4枚を足して144枚**にした。
テストは「花牌・季節牌以外がちょうど34種×4枚」と「合計144枚」の両方を見張っている。

## 2026-08-13：ツールに「在職老齢年金 計算機」を追加した

`tools/lib/zaishoku-rorei-nenkin.ts`（支給停止額・改正前との比較・年度別の基準額）・
`tools/app/zaishoku-rorei-nenkin/`（画面）・`tools/tests/zaishoku-rorei-nenkin.test.ts`（35件）。
`tools/lib/registry.ts` と `home/index.html` の一覧にも足した。
仕様は [features/zaishoku-rorei-nenkin.md](./features/zaishoku-rorei-nenkin.md)。

**理由**：令和7年年金制度改正法（令和7年法律第74号）で令和8年4月から
支給停止調整額が月51万円→65万円に上がった。「お金・社会保険」の既存6本は
すべて払う側の計算で、年金の給付を扱うものが1本も無かった空白を埋める。

**「62万円」ではなく「65万円」であることを独自価値に置いた。**
解説記事の多くが「62万円に引き上げ」と書いているが、62万円は法律上の
令和6年度水準の額で、実際に適用される額ではない。支給停止調整額は毎年度
賃金の変動に応じて改定され、令和8年度に使われる額は65万円である
（実装時に日本年金機構の2ページで再確認済み・2026-08-13）。
賃金と年金の合計が62万〜65万円の帯にいる人は、62万円で計算すると
「年金が減る」と誤って出るが実際は全額支給で、3万円ぶんの帯で結論が逆になる。
テストでこの帯を固定した。

**年金額そのものは計算せず、定期便の数字を入れてもらう設計にした。**
報酬比例部分の額は全期間の標準報酬月額の履歴と加入月数から決まり、
利用者が入力できる情報ではない。推計にすると答えの精度が推計の精度に引きずられる。

**支給停止調整額は年度をキーにした表（`FISCAL_YEARS`）で持った。**
毎年度改定されるため、定数を1箇所にまとめて更新箇所であることを明示している。
標準報酬月額は `lib/shaho-grades.ts` の `pensionStandardMonthly()` をそのまま使い、
新しい等級表を持たない（1箇所直せば支援金・傷病手当金・働き損・このツールの4本に効く）。

**加給年金額を任意入力として足した**（仕様書の入力表には無い）。
仕様書の境界条件「全部支給停止のときは加給年金額も止まる」を
金額として出すには額が要るため。空欄なら受取総額に含めない。

**日本年金機構の「在職老齢年金早見表」（PDF）との突き合わせはできていない。**
PDFがサブセットフォント埋め込みで、この環境ではテキストを取り出せなかった。
代わりに一次情報のページに載っている計算例（基本月額10万円・総報酬月額相当額46万円
→ 改正前は2.5万円停止・改正後は全額支給）をテストで固定している。

## 2026-08-13：取りこぼしていた4ページに自己参照canonicalを足し、テストで見張るようにした

`tools/app/page.tsx`・`games/app/page.tsx`・`tools/app/privacy/page.tsx`・
`games/app/privacy/page.tsx` に `alternates.canonical` を足した。
回帰テストとして `tools/tests/canonical.test.ts` と `games/tests/canonical.test.ts` を新設。
仕様は [features/self-canonical-coverage.md](./features/self-canonical-coverage.md)。

**理由**：`app/` 配下の `page.tsx` 34件のうち、この4件だけが canonical を持っていなかった。
`layout.tsx` は `metadataBase` を持つが `alternates` を持たないため、ページ側が書かないと
`<link rel="canonical">` は1つも出力されない。本番HTMLと Search Console の URL検査API でも
`userCanonical` が null であることを確認した（2026-08-13）。
とくに `/games/` はゲーム9本を束ねるハブで、かつ「検出 - インデックス未登録」のままだった。

**インデックス未登録31件の主因はこれではない。** 新URL構成への切り替えが2026-08-08で
まだ5日しか経っておらず、新規ドメインで31件が未登録なのは普通の状態である。
それでも直したのは、canonical が無いページは重複判定で**こちら側の主張ができない**ため。
旧サブドメインが正規URLとして選ばれている6件はいずれもページ側が新URLを主張しており、
canonical は必ず従わせるものではないが、主張が無いと勝ち負けにすら参加できない。
工数がほぼゼロなので、効果の大小を議論するより先に埋めるのが安い。

**テストのほうが本体より重い。** この取りこぼしは「モノレポ統合で申し送りが落ちた」
という経路で起きたので、人間の注意力ではなくテストで止める。
`search-index-consolidation.md` に残っていた移送先（アーカイブ済みリポジトリの
`section-index-canonical.md`）は、どちらにも存在しないままだった。

**`layout.tsx` に既定の canonical を置く案は採らなかった。** 一見4ページとも解決するが、
ページ側が `alternates` を書き忘れたとき全ページがセクショントップを正規URLとして
主張してしまう。取りこぼしが「canonicalが無い」から「canonicalが間違っている」に変わり、
後者のほうがはるかに危険（OGPで踏んだ浅い上書きの落とし穴と同じ構造）。

**セクショントップに title / description は書いていない。** `layout.tsx` の
`title.template` が `'%s'` なので、ページ側に `title` を書くと `title.default` が消える。
文言を変える意図は無いので `alternates` だけを持つ `metadata` にした
（ビルド後の `<title>` が変わっていないことを確認済み）。

## 2026-08-12：ツールに「年末調整 還付金 計算機」を追加した

`tools/lib/nenmatsu-chosei.ts`（年調年税額・還付額・令和7年分との比較）・
`tools/app/nenmatsu-chosei/`（画面）・`tools/tests/nenmatsu-chosei.test.ts`（41件）。
`tools/lib/registry.ts` と `home/index.html` の一覧にも足した。
仕様は [features/nenmatsu-chosei-kanpu.md](./features/nenmatsu-chosei-kanpu.md)。

**理由**：令和8年分は基礎控除の特例加算42万円（令和8・9年分だけの時限措置）が
初めて年税額に効く年末調整で、例年より大きな還付が広く出る。検索需要は10月から
立ち上がるので、8月に出しておけばインデックスされる時間がある。
年末調整のツールはサイトに1本も無かった。

**源泉徴収税額の実額入力を主にした。** 還付額は「源泉徴収の累計 − 年税額」で決まり、
前者は利用者が給与明細で持っている。月次表を実装せずに済むので、
賞与の配分や月ごとの変動によるずれを丸ごと回避できる。

**仕様書の「要確認事項」を国税庁の原文で確認したら、結論がひっくり返った。**
基礎控除の引上げ・給与所得控除の最低保障額の引上げ・扶養親族等の所得要件の改正は
**令和8年12月1日施行**で、「令和8年11月までの給与等の源泉徴収事務に変更は生じません」と
明記されている（[令和8年4月 源泉所得税の改正のあらまし](https://www.nta.go.jp/publication/pamph/gensen/2026kaisei.pdf) 2ページ、
[Ｑ＆Ａ](https://www.nta.go.jp/users/gensen/2026kiso/pdf/0026005-024.pdf) Ｑ１－１）。
源泉徴収税額表そのものの改正は令和9年1月1日施行。
つまり**「月次表に特例加算がどこまで入っているか」という問い自体が消え、答えは「1円も入っていない」**。
減税分はまるごと12月の年末調整で精算される。これを受けて推計モードを
改正前（令和7年分）の控除額で計算するよう直した。当初は令和8年分の控除額で
源泉徴収されている前提で書いており、**年末調整でしか効かない控除が無い人の還付を
0円と表示していた**（正しくは給与収入500万円・独身で28,300円）。答えが正反対だった。

扶養親族等の所得要件も同じ資料で確認し、**62万円以下（給与収入136万円以下）で正しかった**
（仕様書の「58万円以下」は改正前の値）。ついでに `lib/furusato-nozei.ts` の
基礎控除・給与所得控除・配偶者特別控除・特定親族特別控除の定数もあらましの表と
突き合わせたが、**誤りは無かった**。

税額計算の中核は `lib/furusato-nozei.ts` の `salaryDeduction()` / `basicDeductionIncomeTax()` /
`incomeTaxAmount()` / `applyHousingLoan()` をそのまま再利用している。新しく書いたのは
配偶者特別控除・特定親族特別控除の表と、年調年税額（102.1%・100円未満切捨て）の段だけ。

**独自価値は「令和7年分の控除額で計算した場合」との差額**に置いた。
給与収入500万円・独身なら 119,400円 → 91,100円 で28,300円の減税になる。
「今年はなぜ還付が多いのか」を金額で見せられるのは、時限措置の初年度である
令和8・9年分の2年だけ使える切り口。比較用に令和7年分の給与所得控除（最低保障65万円）と
基礎控除を新たに定数として置いた。

## 2026-08-12：SNS共有時のサムネイル（OGP画像）を入れた

`design/ogp/gen-ogp.mjs`（生成スクリプト）と、そこから書き出した1200×630のPNGを3枚

**理由**：`og:image` も `twitter:card` も全ページに無く、X・LINE・Slack に貼ると

まず差を埋めて案Aは別PRに分ける。

ページごとに作る案Aの話。案Bの3枚は registry を触っても増えないので、

日本語のWebフォントは埋め込まず、生成時の端末フォント（Hiragino / Noto Sans JP /

アクセントは forest green 1色のままなので配色からは外れない。

**踏んだ落とし穴**：Next.js のメタデータは入れ子のオブジェクトを浅く上書きするため、
ページ側が `openGraph: { url: ... }` と書いた瞬間に layout の `images` ごと消える。
`{tools,games}/tests/ogp.test.ts` が app/ 配下を走査して見張っている。
`twitter` も `openGraph` から画像を引き継がないので `card` と `images` を明示した。

## 2026-08-12：全ページにパンくず（BreadcrumbList + 視覚ナビ）を入れた

`tools/lib/jsonld.ts`・`games/lib/jsonld.ts`（`breadcrumbTrail` / `breadcrumbFor` /
`breadcrumbList`）と `tools/app/Breadcrumb.tsx`・`games/app/Breadcrumb.tsx`。
tools・games の全ページ（404を除く）の `h1` の直前に「ホーム ＞ サイト名 ＞ 現在地」を出し、
既存の `@graph` に `BreadcrumbList` を1要素足した。`home/` は最上位なので入れていない。
仕様は [features/breadcrumbs.md](./features/breadcrumbs.md)。

**理由**：ドメイン統合でURLの階層が1段深くなり（`tool.hasokon.com/sleep-cycle/` →
`hasokon.com/tools/sleep-cycle/`）、検索結果の表示が「hasokon.com › tools › sleep-cycle」に
なっていた。`BreadcrumbList` があれば日本語のパンくずで出せる。
個別ページから一覧に戻る導線がヘッダーのサイト名しか無かったことへの対策でもある。

表示と構造化データは**同じ `Crumb[]` から作る**。`breadcrumbFor(slug)` が返すのは
`BreadcrumbList` ではなく段の配列で、ページはそれを `<Breadcrumb>` と `breadcrumbList()` の
両方に渡す。片方だけ直して食い違うのを構造で防ぐため。名前は registry から引くので、
ツールを1本足せばパンくずにも自動で載る（未登録の slug は投げてビルドが落ちる）。

`<script>` は増やしていない。`privacy` / `contact` と動的ルート（`r/[slug]` / `guide/[slug]`）は
JSON-LD が単体オブジェクトだったので `@graph` 形式に変えて中に足した。

`tools/tests/jsonld.test.ts` / `games/tests/jsonld.test.ts` が、
末尾の段に `item` を付けないことに加えて、**registry の全 slug のページが
パンくずを出していること**と **ld+json が1ページ1枚のまま**であることを見張っている。

## 2026-08-12：ゲームに「リバーシ」を追加した（対戦相手のいる最初の1本）

`games/lib/reversi.ts`（盤面・合法手・裏返し・パス・終局判定・CPU）・
`games/app/reversi/`（画面）・`games/tests/reversi.test.ts`（50件）。
`lib/registry.ts` と `home/index.html` の一覧にも足した。
仕様は [features/game-reversi.md](./features/game-reversi.md)。

**理由**：既存8本がすべて一人用で、対戦相手のいるゲームが1本もなかった。

## 2026-08-11：GA4のページビューから `page_path` を外した

`basePath` を `lib/analytics.ts` にも書いて二重管理するより消すほうが素直。

**⚠️ 2026-08-08 から本修正が本番に出るまでの `pagePath` は信用しないこと。**
GA4に遡及変更の手段はないので、この期間を含む分析では `pagePath` ではなく
`fullPageUrl` を使う（旧データも実際のURLで読める）。同じ期間、
tools と games の `privacy`・`contact` は `/privacy/`・`/contact/` に潰れていて、
どちら側のページかは `pagePath` からは区別できない。
