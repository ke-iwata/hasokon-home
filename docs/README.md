# docs の使い方

このフォルダは **「どういう理由で、何を作った／作らなかったのか」を残し続ける場所**です。
コードを読めば「何をしているか」は分かりますが、「なぜそうしたか」は残しておかないと失われます。

## 置くもの

| ファイル | 内容 |
|---|---|
| [DECISIONS.md](./DECISIONS.md) | 実装した機能と、その理由の記録。**新しく何か作ったら必ず追記する** |
| [features/](./features/) | 機能仕様書。1機能 = 1ファイル。実装前の提案もここに置き、実装後もそのまま残す |

## 書き方の約束

1. **理由を書く。** 何をしたかはgit履歴に残る。ここに書くのは「なぜそれを選んだか」
   と「他の選択肢をなぜ採らなかったか」
2. **数字を根拠にする。** 計測データがあるなら、取得日と数値を残す。
   あとから「その判断は正しかったか」を検証できるようにするため
3. **やらなかったことも書く。** 提案を見送った場合、見送った理由を書いておかないと
   半年後に同じ提案が繰り返される

## 並走ブランチとコンフリクトの約束

機能実装を並走させても docs がコンフリクトしないよう、次のルールで運用する
（2026-08-11 導入。それまで DECISIONS.md と features/README.md が毎回衝突していた）。

1. **DECISIONS.md（ルート・tools・games）は union マージ**（`.gitattributes`）。
   複数ブランチが同時に追記しても、両方のエントリが自動で残りコンフリクトしない。
   このために書き方を守ること:
   - 新しいエントリは**冒頭の `---` の直下**に、`## 日付：タイトル` から始まる
     **1つの自己完結したブロック**として足す（前後に空行を1行ずつ）
   - **既存エントリの本文を同じPRで書き換えない**（union は行単位の機械的な統合
     なので、同じ行の同時編集は黙って両方残る。直すときは単独のPRで）
   - マージ後にエントリの順序が日付順からずれることがあるが、実害はないので
     気づいたときに直せば足りる
   - **GitHubのマージボタンは union マージを使わない。** `.gitattributes` の
     merge ドライバが効くのは**手元の `git merge` だけ**で、GitHub側（画面の
     マージボタン・API）は素の三方向マージをするため、**DECISIONS.md は
     ふつうに衝突扱いになる**。つまり並走した2本目以降は、**PRをマージする前に
     `git merge origin/main` で main を取り込んで push する**必要がある
     （取り込みは手元で行うので union が効き、手で直すところは出ない）。
     この非対称性を知らないと「union なのになぜ衝突するのか」で止まる
     （2026-09-01 に #171・#172 の2本が同じところで足止めされた）
2. **features/README.md に一覧・状態の表を持たない。** 状態は各仕様書の冒頭の
   `**状態**：` 行だけで管理する（詳細は [features/README.md](./features/README.md)）。
   仕様書の追加・更新で README を触る必要はない
