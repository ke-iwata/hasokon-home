## 提案1：ドメイン統合の再クロールを加速する（最優先・SEO）

### 根拠

URL検査で**6ページが「Googleが別のページを正規と判定」**になっており、
選ばれた正規URLは旧ドメイン（`tool.hasokon.com` / `game.hasokon.com`）でした。

ただし、これは**301が壊れているという意味ではありません**。最終クロール日時を見ると切り分けられます。

| ページ | Googleが選んだ正規URL | 最終クロール |
|---|---|---|
| `/tools/nenshu-kabe/` | `tool.hasokon.com/nenshu-kabe/` | 2026-08-07 16:55 |
| `/tools/roulette/` | `tool.hasokon.com/roulette/` | 2026-08-07 17:00 |
| `/games/minesweeper/` | `game.hasokon.com/minesweeper/` | 2026-08-07 17:00 |
| `/tools/kosodate-shienkin/` | `tool.hasokon.com/kosodate-shienkin/` | 2026-08-07 17:00 |
| `/tools/shobyo-teate/` | `tool.hasokon.com/shobyo-teate/` | 2026-08-07 23:03 |
| `/tools/aircon-denkidai/` | `tool.hasokon.com/aircon-denkidai/` | 2026-08-07 23:03 |

**6件すべて、クロールがドメイン統合のデプロイ（2026-08-08）より前です。**
一方、統合後にクロールされたページは全部 PASS になっています。

| ページ | 最終クロール | 判定 |
|---|---|---|
| `/` | 08-08 23:31 | PASS |
| `/tools/furusato-nozei/` | 08-09 01:38 | PASS |
| `/tools/` | 08-10 08:32 | PASS |
| `/tools/sleep-cycle/` | 08-10 10:11 | PASS |

移行の仕組み自体は正しく動いていると考えられます。残っているのは**再クロール待ちの6件**です。
放置しても直る可能性は高いものの、旧URLが正規のままだと新URLは検索結果に出ないので、期間を短縮する価値があります。

### 提案する対応

1. **旧ドメインを Search Console のプロパティとして登録し、アドレス変更ツールを実行する**
   `tool.hasokon.com` と `game.hasokon.com` をプロパティ追加 →「設定 > アドレス変更」で `hasokon.com` を指定。
   サイト移転を Google に明示的に伝える正規の手段で、再クロールを待つより速い
2. **旧ドメインのサイトマップを当面残す**
   URL検査の「参照元」を見ると、`/tools/hebon-romaji/` などは `tool.hasokon.com/sitemap.xml` 経由で
   発見されています。旧サイトマップが生きているうちは Google が旧URLを再クロールし、301を見つけられる。
   移行が終わるまでは消さないほうがよい（Google の移転ガイドラインでも推奨されている）
3. **301が実際に返っているかを確認する**
   このセッションの実行環境はネットワークポリシーで hasokon.com へ到達できず、HTTPレスポンスを直接確認できませんでした。
   手元で以下を実行して 301 と Location を確認してください。1〜2 が空振りするとしたら原因はここです。
   ```bash
   curl -sI https://tool.hasokon.com/nenshu-kabe/ | head -5
   curl -sI https://game.hasokon.com/minesweeper/ | head -5
   ```
   リダイレクト設定は [hasokon-infra](https://github.com/ke-iwata/hasokon-infra) の管轄です

### 期待できる効果

インデックス対象が実質4ページから10ページに増えます。
特に `/tools/nenshu-kabe/`（年収の壁）は制度改正対応で競合優位がある本命ページなので、
これが新URLで正規化されないと流入が立ち上がりません。

### 工数

**半日程度。コード変更なし**（Search Console の設定作業とインフラ側の確認）。

## 提案2：インデックス未登録13ページの導線を作る（SEO・内部リンク）

### 根拠

「検出 - インデックス未登録」9件と「未認識」3件、合わせて**12ページがまだ一度もクロールされていません**。
特に games は深刻で、9ページ中インデックス済みが0、`/games/` 自体も未クロールです。

URL検査の「参照元」に注目すると、発見経路が偏っているのが分かります。

| ページ | 発見された参照元 |
|---|---|
| `/tools/group/`、`/tools/dice/` | `/tools/nenshu-kabe/`（＝旧ドメインが正規と判定されている弱いページ） |
| `/tools/hebon-romaji/` ほか3件 | `tool.hasokon.com/sitemap.xml`（旧サイトマップのみ） |
| `/games/` および games 配下 | 参照元なし（サイトマップのみ） |

トップページ（`/`）からは全ツール・全ゲームにリンクが張られていますが、
**Googleの認識上はまだ「サイトマップにしか載っていないページ」の扱い**です。
新しいサイトではサイトマップだけでクロールを引き出すのは難しく、内部リンクの厚みが要ります。

### 提案する対応

1. **`/tools/` と `/games/` を相互にリンクする**
   現在、tools と games のセクショントップは互いにリンクしていません。
   両サイトのフッターは `hasokon.com` トップにしか繋がっていないので、
   1ホップ余計にかかります。姉妹サイトへの導線を直接張る
2. **パンくず（BreadcrumbList）を入れる**
   `hasokon.com > 無料計算ツール集 > 年収の壁 計算機` のような構造化データ。
   検索結果の表示が変わるだけでなく、階層をGoogleに明示できる。
   tools / games とも各ページに JSON-LD を出す仕組みが既にあるので追加は軽い
3. **games にも関連リンクの一覧を確実に出す**
   tools には `app/RelatedTools.tsx` があります。games の各 `page.tsx` にも
   「他のゲーム」の一覧はありますが、tools と同じ共通コンポーネントに揃えると
   ゲーム追加時のリンク漏れがなくなる
4. **トップページのカード一覧をレジストリと同期する仕組みを検討する**
   `hasokon-home/index.html` のカード一覧は tools / games のレジストリと**手動同期**です
   （ファイル内のコメントにもそう書かれています）。ツールを増やしたときにトップから
   リンクが漏れると、いま起きているのと同じ「サイトマップにしかないページ」が生まれます

### 期待できる効果

クロール対象が広がり、games 9ページの立ち上がりが早くなります。
1〜3 は「順位を上げる施策」ではなく「土俵に乗せる施策」なので、効果の出方は明確です。

### 工数

- 1・3：各リポジトリ半日
- 2（パンくず）：tools / games 各半日
- 4：1日（レジストリのJSONを home にビルド時コピーする等、方式の検討を含む）

## 提案3：ルートドメインが GA4 で計測されていない（計測の欠損）

### 根拠

**いま唯一クリックを得ているページ（`hasokon.com/`、3クリック中3クリック）が計測対象外です。**

`hasokon-home` の静的HTMLに GA4 のタグが1つも入っていません。

```
index.html   : gtag / googletagmanager の出現 0回
404.html     : 0回
privacy.html : 0回
```

tools / games 側は `lib/analytics.ts` に測定ID `G-2Z0K6Y2FX0` が設定済みで計測されています。
`lib/analytics.ts` のコメントにも「hasokon.com も同じIDで計測するなら index.html / 404.html にも
同じタグを入れる」と書かれていますが、この作業が未了です。

結果として、**トップページに来た人が tools と games のどちらへ流れたのかが分かりません。**
トップはリンク集なので、ここの遷移率こそが一番見たい数字です。

あわせて、**この定期タスクは GA4 のデータをAPIで取得できませんでした。**

```
Google Analytics Admin API has not been used in project 495907315040 before or it is disabled.
```

GCPプロジェクト `hasokon-site` で Analytics Admin API / Data API が無効になっています。

### 提案する対応

1. `hasokon-home/index.html`・`404.html`・`privacy.html` の `<head>` に GA4 のタグを追加する
   （tools と同じ測定ID。`<head>` に生タグで置く方針は tools の layout.tsx に合わせる）
2. GCPプロジェクト `hasokon-site` で **Google Analytics Admin API** と **Google Analytics Data API** を有効化する
3. サービスアカウント `claude@hasokon-site.iam.gserviceaccount.com` を GA4 プロパティの「閲覧者」に追加する

### 期待できる効果

- トップページ → tools / games の遷移率が見えるようになり、カードの並び順・文言の改善が数字で判断できる
- 2・3 によって、この定期タスクが次回から GA4 の行動データ（直帰率・滞在時間・`tool_use` イベント）を
  使えるようになる。現状は Search Console の数字（クリック3件）だけで、UX の判断材料がない

### 工数

**1〜2時間。** 1 はHTML3ファイルに数行、2・3 はコンソール作業のみ。

## 提案4：OGP画像の追加と、統合で生まれた重複ページの整理（UI/UX・CTR）

### 根拠

**`og:image` が3リポジトリすべてに1つもありません。**

- `hasokon-home/*.html`：`og:image` の出現 0件
- `hasokon-tools/app/layout.tsx`：`openGraph` に `type` / `siteName` / `locale` のみ
- `hasokon-games/app/layout.tsx`：同上

LINE・X・Slack などに貼られたときにリンクカードが無地になります。
計算ツールは「これ便利だよ」と共有されて広がる性質があるので、
検索以外の入口を作るうえで効きます。

もう1点、ドメイン統合の副作用として**同一ドメイン内に同じ役割のページが重複しています**。

| 役割 | URL |
|---|---|
| プライバシーポリシー | `/privacy.html`、`/tools/privacy/`、`/games/privacy/` |
| お問い合わせ | `/tools/contact/`、`/games/contact/` |

サブドメインで別サイトだった頃は必要でしたが、いまは1ドメインです。
実際 `/privacy.html` は掲載順位16位で1回表示されており、
**貴重な表示回数がポリシーページに使われています。**

### 提案する対応

1. 3サイト共通のOG画像を1枚作り、各 layout / HTML の `og:image` に設定する
   （ツールごとに変える必要はない。まずは共通1枚で足りる）
2. プライバシーポリシーを `/privacy.html` に一本化し、`/tools/privacy/` と `/games/privacy/` は
   canonical をルートに向けるか、リンク先をルートに変える。お問い合わせも同様に統一する
   - AdSense の審査要件としてポリシーページはサイト内に必要なので、**削除ではなく集約**にする

### 期待できる効果

- SNS・チャットからの流入とクリック率の改善
- 重複ページの整理で、クロールバジェットが本来の計算ツールに回る

### 工数

- 1（OG画像）：1日（画像デザイン込み。ロゴ流用なら半日）
- 2（重複整理）：半日

## 次回この調査をするときの注意

- **GA4 は現状APIで取得できません**（提案3-2 が未了の間）。Search Console のみで判断することになります
- 実行環境のネットワークポリシーで `hasokon.com` へ直接HTTPアクセスできません。
  HTTPヘッダ（301・キャッシュ・圧縮）やページ表示速度の実測はこの環境からは不可能です。
  Search Console の URL Inspection API は googleapis.com 経由なので利用できます
- 検索データはまだ4日分しかありません。次回はクエリが出てくる可能性があるので、
  `dimensions: ['query']` を最初に確認するとよいです

## 調査に使ったAPI

| 用途 | エンドポイント |
|---|---|
| クリック・表示・順位 | `webmasters/v3/sites/{site}/searchAnalytics/query` |
| サイトマップの状態 | `webmasters/v3/sites/{site}/sitemaps` |
| ページ単位のインデックス状況 | `searchconsole.googleapis.com/v1/urlInspection/index:inspect` |
