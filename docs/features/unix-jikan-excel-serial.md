1. **和暦と曜日を出さない。** 日本の業務（申請書・社内報告）では「令和8年11月5日（木）」の形で書き写すことが多い。

   UNIX時間とは別のツールに分かれていることが多い。**「数字を貼ったら日時が出る」という同じ動作で両方を受ける**
3. **ログを丸ごと貼れない（または英語のみ）。** サーバーのログや API の応答をそのまま貼ると、
   中の 10 桁・13 桁の数字の横に日本時間を添えて返す。1 つずつコピーし直す手間を消す

## 提案する仕様

### 入力と出力

**上段：数字 → 日時**（入力欄 1 つ。入力が止まって 150ms 後に計算）

| 入力 | 判定 | 出力 |
|---|---|---|
| 10 桁前後の整数（例 `1793836800`） | UNIX時間（秒） | 日本時間・UTC・和暦・曜日・ISO 8601・「いまから◯日前／後」 |
| 13 桁（例 `1793836800000`） | ミリ秒 | 同上（ミリ秒まで表示） |
| 16 桁・19 桁 | マイクロ秒・ナノ秒 | 同上 |
| **整数部が** 1〜6 桁の数（例 `46331`・`46331.5`） | **Excel のシリアル値の候補** | 同上。小数部は時刻 |
| 整数部が 7 桁以上の小数（例 `1793836800.123456`。Python の `time.time()` など） | 整数部の桁で秒／ミリ秒…を決め、小数部はそれより細かい単位 | 同上（ミリ秒まで表示。それより細かい桁は切り捨てて「以下切り捨て」と注記） |

- **判定は自動だが、判定結果を必ず画面に書き、切り替えボタンで直せる**（「秒として読みました ▸ ミリ秒として読む／Excel のシリアル値として読む」）。
  桁の境目で黙って取り違えるのが競合の弱点なので、ここを見える化する
- 判定の閾値（実装で `lib/` の定数にして、テストで固定する）：
  - **判定はすべて整数部の桁数（絶対値の整数部）で行う。小数かどうかでは決めない**
  - 整数部の絶対値が `1e11` 未満 → 秒、`1e14` 未満 → ミリ秒、`1e17` 未満 → マイクロ秒、それ以上 → ナノ秒
  - ただし `0 < 値 < 1000000`（**6 桁以下**。シリアル値で西暦 4637 年まで。Excel の上限 9999-12-31 は `2958465` だが、7 桁は秒として読むほうが実務で多い）→ Excel のシリアル値を第一候補にし、
    「UNIX時間（秒）として読むと 1970-01-◯◯」も併記する（6 桁以下の秒は 1970 年 1〜12 日目で、実務で出てくることはまれ）
- テストの境界値：`999999`（Excel）・`1000000`（秒）・`46331.5`（Excel・12:00）・`1793836800.123456`（秒・.123）・`99999999999`／`100000000000`（秒／ミリ秒の境）
- 負の値も受ける（1970 年より前）。上限は JavaScript の `Date` の範囲（±8.64e15 ミリ秒）で、超えたら「範囲外」と出す

**下段：日時 → 数字**

- 日付（`input type="date"`）と時刻（`input type="time"` step=1）、タイムゾーンは「日本時間／UTC」の切り替え（既定は日本時間）
- 出力：UNIX時間（秒）・ミリ秒・Excel のシリアル値（1900 年基準）・ISO 8601。それぞれ横にコピーのボタン
- **Excel のシリアル値は、日本時間／UTC の切り替えに関わらず、入力した見たままの日時から出す**（シリアル値にはタイムゾーンが無いため。切り替えで変わるのは UNIX時間・ミリ秒・ISO 8601 だけ。そう注記する）
- 1900-02-28 以前の日付は 1〜59 の側で出す（`60` の欠番を考慮）。1900-01-01 より前は「Excel では表せません」と出す
- 「いまの時刻」ボタンで現在を入れる。**ページを開いた瞬間の UNIX時間を上部に1秒ごとに更新して出す**
  （「unixtime 現在」の検索に応える。`requestAnimationFrame` ではなく 1 秒の `setInterval`、タブが裏のときは止める）
- **現在時刻と「いまから◯日前／後」はマウント後にだけ描画する**（静的エクスポートなので、初期 HTML に焼くとビルド時刻が残り、ハイドレーションもずれる。初期 HTML では `—`）
- 毎秒変わる表示には `aria-live` を付けない（スクリーンリーダーが毎秒読み上げるため）

**ログ欄（折りたたみ。既定は閉じる）**

- 複数行を貼ると、行中の 10 桁・13 桁の数字（前後が数字・英字でないもの）の直後に `［2026-11-05 09:00:00 JST］` を添えて返す
- 誤検出（電話番号・注文番号・ID）を避ける規則。**すべて満たすものだけ**添える：
  1. 先頭が `0` のものは拾わない（`0312345678` など）
  2. 直前が小数点 `.`・ハイフン `-`・スラッシュ `/` のものは拾わない（版番号・日付・パスの一部）
  3. 読んだ結果が **2000-01-01〜2100-12-31（UTC）** に入るものだけ
- **元の行の文字は一切変えない（追記だけ）**。結果の上に「◯件に日時を添えました」と件数を出す
- 結果は横スクロールではなく折り返し（`white-space: pre-wrap`）
- JSON の `"timestamp": 1793836800` のような値もそのまま拾う。Excel のシリアル値はログ欄では**拾わない**（誤検出が多すぎる）
- 上限 1MB。それ以上は止めて理由を出す

### 計算の約束（テストで固定する）

1. **UNIX時間は 1970-01-01T00:00:00Z からの経過秒。うるう秒は数えない**（POSIX の定義どおり。本文の FAQ にも書く）
2. **日本時間は UTC+9 固定**で計算する（日本は 1952 年以降サマータイムが無い。ブラウザの `Intl` のタイムゾーンに任せず、
   `+9h` を足してから UTC の各部を読む。利用者の PC のタイムゾーンが日本以外でも結果を変えないため）
3. **Excel のシリアル値（1900 年基準）**：`1` = 1900-01-01。Excel は 1900 年をうるう年として扱う
   （Lotus 1-2-3 との互換のための既知の仕様で、存在しない 1900-02-29 が `60`）。したがって
   - `シリアル値 ≥ 61` は `1899-12-30` を 0 日目として日数を足す
   - `1 ≤ シリアル値 ≤ 59` は `1899-12-31` を 0 日目として日数を足す
   - `60` は「1900-02-29（Excel だけにある日付）」と出す
   - 小数部は 1 日に対する割合で時刻にする（`0.5` = 12:00:00）。**秒は四捨五入**（`0.1` 秒単位の誤差で 23:59:59 が 00:00:00 に転ばないよう、ミリ秒に直してから丸める）
   - シリアル値には**タイムゾーンが無い**（Excel のセルに入っている「見たままの日時」）。日本時間・UTC の区別を出さず、そう注記する
4. **Mac の古い Excel の 1904 年基準**は、切り替え（「1904 年基準として読む」）で受ける。差は 1462 日
5. 和暦は **`tools/lib/nenrei.ts` の `toWareki()` を流用する**（日数計算には和暦の関数は無い）。
   **1873-01-01（`GREGORIAN_START`）より前は和暦を出さない**（明治5年12月2日以前は旧暦で、月日が西暦と対応しないため。`toWareki()` が `null` を返す扱いに合わせる）。
   改元日の境目（1989-01-07 は昭和64年、01-08 は平成元年。2019-04-30 は平成31年、05-01 は令和元年）と 1872-12-31／1873-01-01 をテストに入れる
6. **2038 年問題の境目**：`2147483647` は 2038-01-19 03:14:07 UTC（日本時間 12:14:07）。入力がこの前後なら
   「32 ビットの符号付き整数で表せる最後の秒です」と一言添える（エンジニア向けの小ネタで、被リンクを呼びやすい）
