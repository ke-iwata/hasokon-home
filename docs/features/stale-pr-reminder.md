# 開きっぱなしのPRを催促する（セッションが落ちても止まらない見張り）

**状態**：実装済み（2026-09-18。`main` にマージされてから定期実行が始まる）
**対象**：`.github/workflows/pr-reminder.yml`、`scripts/stale-prs.mjs`（hasokon-infra にも同じものを置く想定）
**起票**：2026-09-18

---

## 背景と根拠

### PRが放置されるのは「見張りがセッションの中にいる」から

このリポジトリのPRは、ほとんどが定期ルーチンから生まれる。提案（`docs:`）・
実装（`feat:`）・レビューのそれぞれにルーチンがあり、どれも指示の最後が
**「PRは1時間おきに確認して、コメントがあれば対応してください」**で終わっている。

つまり**見張りの役目がセッションの中にある**。やり取りが増えてセッションが落ちると、
その瞬間に見張りも消える。PRだけがGitHubに残り、誰も戻ってこない。
2026-09-18 時点で hasokon-home に12本・hasokon-infra に5本のPRが開いたままで、
最古は8日前（[#202](https://github.com/ke-iwata/hasokon-home/pull/202) /
[#203](https://github.com/ke-iwata/hasokon-home/pull/203)）だった。

### GitHubの通知は、この構成では鳴らない

- PRテンプレートも CODEOWNERS も無い
- 全PRで assignee・reviewer が未設定
- リポジトリのコラボレーターは運営者1人で、**ルーチンが作るPRの作者も同じアカウント**

GitHubは**自分のPRに自分をレビュアー指名できない**。ルーチンが作るPRは
作者が運営者自身なので、CODEOWNERS を置いてもレビュー依頼の対象から外れる。
したがって「レビュー依頼の通知で気づく」という普通のやり方は、**いまのPRの作られ方では**
使えない（PRをボット名義で作れば指名できる。それは各ルーチンの設定の話で、
このリポジトリからは変えられない）。

**PR自体へのコメント**なら、作者は購読者なので作られ方によらず必ず通知される。
この仕組みがコメントを選んでいるのはそのため。

## 仕様

`.github/workflows/pr-reminder.yml` の2つのジョブ。

### 1. 毎朝09:00(JST) に、止まっているPRを催促する

`scripts/stale-prs.mjs` が開いているPRを全部見て、**3日動いていないもの**に
コメントを1つ残す。しきい値は `--days`、手動実行時は Actions の入力で変えられる。

「動いた」の判定に **PRの `updated_at` を使わない**。催促コメント自体が `updated_at` を
動かすので、それを見ると催促した瞬間に経過日数が0に戻り、二度と催促が飛ばなくなる。
代わりに**コミット・ボット以外のコメント・レビュー**の最新時刻を見る。

同じPRに毎日積まないよう、直近の催促から `--remind-every` 日（既定3日）は何もしない。
自分の過去のコメントは本文先頭の目印 `<!-- stale-pr-reminder -->` で見分ける。

### 2. PRが開かれたら、assigneeを入れる

レビュアー指名が使えないぶん、**GitHubの「Assigned」に溜まる**ようにする。
入れるのは作者だが、**ボット名義のPR（`claude[bot]` など）は assignee にできない**
（APIが403を返す。実際に [#230](https://github.com/ke-iwata/hasokon-home/pull/230) の
初回実行がこれで落ちた）。その場合はリポジトリのオーナーを入れる。どのみち動かすのは
人なので、「Assigned に溜める」目的はそれで満たせる。

すでにassigneeがいれば何もしない。fork からのPRでは `GITHUB_TOKEN` が
読み取り専用になるので触らない。

### 動かすもの・動かさないもの

- **やること**：コメント、assigneeの付与
- **やらないこと**：PRを閉じる、ラベルで自動クローズ、ブランチの削除。
  放置を見つけるのが目的で、**判断は人がする**

## 決めたこと

- **`stale` ラベルを付けて自動クローズする作りにしない。** このリポジトリのPRは
  提案（`docs:`）が多く、寝かせたものが後で効くことがある。機械が消してよいものではない
- **GitHub Actions に置く。** 定期ルーチン（Claude）側から催促する案もあるが、
  それだと**放置の原因である「セッション頼み」を、別のセッション頼みに置き換える**だけになる。
  GitHub側だけで完結する見張りを1枚持っておく
- **hasokon-infra にも同じものを置く。** PRの出どころが同じルーチンなので、片方だけでは漏れる

## 確認の仕方

```bash
# しきい値の判定とAPI経路のテスト
node --test "scripts/test/stale-prs.test.mjs"

# 実際のリポジトリに対して、コメントせずに対象だけ数える
GITHUB_TOKEN=<token> node scripts/stale-prs.mjs --repo ke-iwata/hasokon-home
```

`main` にマージされるまで定期実行は始まらない（GitHub Actions の `schedule` は
デフォルトブランチのワークフローしか見ない）。マージ後、Actions の
「PR reminder」を手動実行すれば、その場で対象を確認できる。
