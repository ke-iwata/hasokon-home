# 機能ごとに本番リリースから外す仕組み（フィーチャーフラグ）

**状態**：レベル1のみ実装済み（2026-08-17。本番反映はタグリリース待ち）。
レベル2・3は未実装（必要になってから）
**対象**：`games/` `tools/`（`home/` は事情が違う。後述）
**起票**：2026-08-16（運営者の「feature flag みたいなので機能ごとに本番デプロイから
対象外にするとかできたりしない？」から）

## 解きたい問題

いまの流れは「main にマージ → test.hasokon.com」「`v*` タグ → hasokon.com」で、
**1つのタグでサイト全体がリリースされる**。そのため:

- main に入れた時点で、次のリリースに必ず乗る
- 「テスト環境で見てもらいたいが、本番にはまだ出したくない」ものを置く場所がない
- 出したくないものを避けようとすると、機能ブランチを長く持つことになる。
  並走ブランチは docs のコンフリクトを生んで一度対策済み（`docs/README.md`）で、
  同じ問題をまた抱えることになる

## いまの状態（調べたこと）

**1. 本番とテストは「同じ成果物を昇格」していない。別々にビルドしている。**

`deploy.yml` は `actions/checkout@v4` で対象の ref を取り、その場で
`npm run build` して S3 に同期する。タグを打てばタグの中身がビルドされる。

→ **ビルド時に環境で分岐する仕掛けが素直に効く。** 逆に「テストで確かめた成果物
そのものが本番に行く」保証は元から無い（後述の副作用の話につながる）。

**2. `registry.ts` に `ready: boolean` がすでにある。ただし誰も使っていない。**

`games` / `tools` 両方の `GameDef` / `ToolDef` に `ready` があり、
次の3か所が見ている:

- トップページの一覧（`app/page.tsx`）
- 各ページ下部の「他のゲーム」
- `app/sitemap.ts`
- （加えて `scripts/test/llms-txt.test.mjs` が `ready` を基準に llms.txt と突き合わせる）

**現在 `ready: false` のエントリは1つも無い。** つまり仕組みの半分は用意されていて、
使われないまま眠っている。ただし今の `ready` には足りないところが2つある:

- **環境の区別がない。** テストと本番で同じ扱いになる
- **ページ自体は建って配られる。** 一覧から消えるだけで、URLを直接叩けば見える

**3. `home/` にはビルド工程が無い。** 素のHTMLをそのまま S3 に同期している。
ビルド時のフラグは原理的に効かない。ここがこの話でいちばん厄介な制約。

**4. 静的サイトなのでサーバーが無い。** 実行時にフラグを配る仕組み（LaunchDarkly の
ような）は置けない。ブラウザで `location.hostname` を見る手はあるが、
**HTMLの中身は本番にも入る**ので、SEO・AdSense の観点では隠したことにならない。

## 3段階に分ける（入れたのはレベル1だけ）

「本番から外す」と一口に言っても強さが3段階ある。**必要な強さだけ使うのが安い。**

### レベル1「載せない」（`stage` を registry に持たせる。ワークフローは触らない）

**実装済み（2026-08-17）。** `ready: boolean` を `stage: 'wip' | 'preview' | 'public'` に
置き換えた。

| stage | 一覧・sitemap・llms.txt | `robots` | URLを直接叩くと |
|---|---|---|---|
| `wip` | 出さない | `noindex` | 見える |
| `preview` | 出さない | `noindex` | 見える |
| `public` | 出す | 既定 | 見える |

実際に触ったもの:

| ファイル | 変更 |
|---|---|
| `{games,tools}/lib/registry.ts` | `Stage` 型・`stage` フィールド・`publicGames` / `publicTools`・`robotsForStage` / `robotsFor` |
| 一覧・「他のゲーム」・関連ツール・`not-found`・`about` | `filter((x) => x.ready)` をやめて `publicGames` / `publicTools` を通す |
| `app/sitemap.ts`（両方） | 同上 |
| 全ページの `page.tsx`（ゲーム18・ツール27） | `metadata` に `robots: robotsFor('<slug>')` |
| `{games,tools}/tests/stage.test.ts` | 新設（各8件） |
| `scripts/test/llms-txt.test.mjs` | `ready` → `stage` |

- **ワークフローは変えていない。成果物はテストと本番で同じ。**
- 守れるのは「検索から見つかること」「トップから辿れること」。
  **秘密にはできない**（URLを知っていれば見える）

**`publicGames` / `publicTools` を通すこと。`games` / `tools` を直に `filter`
しないこと。** 一覧を出す場所が増えるたびに条件を書き写すことになり、
書き忘れが公開事故になる。

**`robotsForStage` を `robotsFor` と分けてある**のは、registry の中身に関係なく
規則そのものをテストできるようにするため。いま全エントリが `public` なので、
registry 越しにしか見られないと「非公開なら noindex」の確認が書けない。

実際に1本を `preview` にしてビルドし、**sitemap・トップの一覧・「他のゲーム」から
消えて `<meta name="robots" content="noindex, nofollow">` が付く**こと、
**ページ自体は建つ**ことを確認済み（2026-08-17）。

**多くの場合これで足りる。** 実際に困るのは「未完成のページが Google に拾われる」
「AdSense の審査で薄いページとして見られる」「トップから辿れて完成品に見える」で、
どれも載せなければ起きない。

### レベル2「本番には置かない」（`SITE_STAGE` ＋ ビルド後の間引き）

**未実装。** レベル1で足りないとき（＝ファイルそのものを本番に置きたくないとき）
だけ足す。`stage` はそのまま使えるので、足すのはワークフローと間引きスクリプトだけ。

1. `deploy.yml` が環境を渡す。タグなら `SITE_STAGE=production`、main なら `test`
2. registry の `stage` と `SITE_STAGE` を突き合わせ、**ビルド後に `out/<slug>/` を
   消す小さなスクリプト**を `npm run build` の後ろに足す

```
stage: 'wip'     → test にも本番にも置かない（手元だけ）
stage: 'preview' → test には置く、本番には置かない
stage: 'public'  → どちらにも置く
```

**なぜ「そもそも建てない」ではなく「建ててから消す」か。**
App Router の静的書き出しは `app/` のディレクトリを全部書き出す。
ページ単位で建てないようにするには各ページに分岐を入れることになり、
18本すべてに同じ仕掛けを配ることになる。間引きスクリプトなら20行程度で済み、
registry という単一の情報源から一箇所で効く。

S3 同期は `--delete` 付きなので、本番から消えたページは実際に消える。
CloudFront も毎回 `/*` を invalidate しているので残らない。

### レベル3「実行時に出し分け」（採らない）

`location.hostname` を見てブラウザ側で隠す方法。**既定では使わない。**

- HTMLの中身は本番にも入るので、検索エンジンにもソース表示にも見える
- 静的HTMLと表示が食い違うので、出るまでの一瞬ちらつく

採ってよいのは「両方のビルドに存在していなければならないもの」だけ
（例：文言のA/Bテスト）。ページの公開/非公開には使わない。

## `home/` をどうするか

**ビルド工程を足してまでフラグを効かせるのは、やめたほうがいい。**
`home/` を素のHTMLのままにしているのは意図的な選択で（ルート `CLAUDE.md`）、
ビルドを入れると「S3にそのまま同期される」という分かりやすさが失われる。

代わりに**運用の約束**で足りる:

- **トップページのカードと llms.txt の行は、機能を公開するPRで足す。**
  機能そのもののPRでは足さない
- 公開前は「registry に `preview` で入れる」まで。トップに載るのは公開のとき

いま `home/index.html` の更新を機能PRに含めているので、そこだけ分けることになる。

`llms-txt.test.mjs` は `stage: 'public'` のものだけを突き合わせるよう直した（実装済み）。
**この向きの見張りは両方向に効く**：公開中のものが llms.txt に無ければ落ち、
公開前のものが llms.txt に載っていても落ちる。1本を `preview` にしたとき、
llms.txt の行が残っていて落ちることを確認済み。

## 落とし穴（先に書いておく）

- **フラグは「まだ公開していない」ためのもの。「公開したものを引っ込める」用途には
  使わない。** 一度公開したURLは検索インデックスに載っているので、消すと404になる。
  引っ込めるなら 410 かリダイレクトで、それは別の作業
- **テストと本番でビルドが変わる。** レベル2を入れると、テスト環境で確かめた成果物と
  本番の成果物が一致しなくなる。だから**フラグで消す範囲はページ単位にとどめ、
  共通部分（レイアウト・CSS・ライブラリ）を分岐させない**。分岐が共通部分に及ぶと、
  「テストでは動いたのに本番で壊れる」が起こる。ここがレベル2の実質的なコスト
- **フラグは腐る。** 入れたら消す前提で、仕様書の `**状態**：` 行に
  「いつ `public` にするか」を書く。公開PRでフラグごと消す
- **`ready` を消さずに `stage` を足すと二重管理になる。** 置き換えること
- **`stage` を足したら、それを見張るテストも足す。** 「`public` のものは
  sitemap と llms.txt に載っている」「`preview` のものは載っていない」の2本。
  いまの llms.txt テストの延長で書ける

## 見送った案

- **リリースするタグを機能の手前に打つ。** 「次のリリースに乗せたくない」だけなら
  タグを前のコミットに打てば済むが、main の履歴が直線なので「Aは出したいがBは
  出したくない」に応えられない。cherry-pick でリリース用ブランチを作る運用は、
  1人で回すサイトには重すぎる
- **機能ブランチを長く持つ。** これが今の実質的な運用で、今回の相談の出発点。
  並走ブランチのコンフリクト対策を一度やっている以上、また戻すのは筋が悪い
- **環境変数だけでページを出し分ける（registry を使わない）。** 一覧・sitemap・
  llms.txt が registry を単一の情報源にしているので、そこから外れた仕組みを
  足すと更新漏れの箇所が増える
