### 2. 結果の記録の型

- 1陣を引き終えたら、`games/docs/DECISIONS.md` の冒頭 `---` 直下に**1つの自己完結したブロック**を足す
  （例：「2026-11-xx：チェス・囲碁ほか7本の名称は J-PlatPat で問題なし」。区分・引いた日・検索語・結果。union マージの約束どおり既存エントリは触らない）
- 各仕様書の `**状態**：` 行の「J-PlatPat 確認待ち」を「J-PlatPat 確認済み（日付・結果）」に書き換える
- 「あり」のものは名前の候補を仕様書に書き、その1本だけ止める（陣全体を止めない）

### 3. 公開の順番と PR の切り方

- **陣ごとに1本の公開 PR**（`feat:`）。中身は `stage` を `public`・GamePreview の大きい絵・`BOARD` のタイル・`home/index.html` のカード・
  `node scripts/sync-home-card-art.mjs`。2026-11-03 のダウト（#450）と同じ型
- 公開の PR では各仕様書の「公開条件」も満たすこと（テスト環境で遊んで確かめる・CPU の思考時間など）。
  **満たしていないものは同じ陣でも外して次に回す**（陣は確認の単位で、公開の単位ではない）
- 陣の中の順番は「リバーシ型の CPU 対戦 → 一人用パズル」。理由は上の計測値（滞在の 84% が CPU 対戦）

### 4. 今後の止め札を増やさない（新規提案の書き方）

- 新しいゲームの提案は、仕様書に**確認シートの1行（slug・表示名・検索語・区分）**を必ず書く。運営者はその行をこの表に写すだけで済む
- **公開待ちが 20本を超えている間は、新しいゲームの提案より公開の作業を先にする**（定期の企画ルーティンの判断材料）
