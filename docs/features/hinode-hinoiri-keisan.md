## 背景と根拠

### なぜこのツールか

- **年末年始の検索の受け皿が足りない**。いま年末に向けて立っているのは年末調整・ふるさと納税・お年玉（#494 提案中）・連休計算で、
  ほぼ「お金」と「日付」。**「初日の出 何時」**は年に1回、全国で確実に立つ大きな検索で、計算で一意に答えられる
- 権利・法令のリスクがない：天文計算は公知の式。地点のデータは国土地理院の公表値（政府標準利用規約で出典の記載により利用可）
- 計算サイトの定番（日の出・日の入りの計算は生活・天文の分類で必ずある）なのに、hasokon.com には天文・暦の計算が1本も無い
- [tools/docs/CONCEPT.md](../../tools/docs/CONCEPT.md) の「1ページ1機能・入れたら答えが出る・保守が少ない」に合う。
  記事を書き続ける必要がなく、年が変わっても計算が自動で追従する

### 需要と競合（2026-11-14 の Web 調査）

- 一次情報は**国立天文台 暦計算室「各地のこよみ」**（https://eco.mtk.nao.ac.jp/koyomi/dni/ ）。正確だが、
  地点と年月を選んで表を出す作りで、**「初日の出を47地点で並べる」「冬至・夏至と比べる」「昼の長さの差」**は自分で読み比べる必要がある
- 民間の計算サイト・天気サイトは広告が重く、初日の出の一覧は年末だけ記事で出る（年が変わると古い）
- 「初日の出 2027」「冬至 日の出 何時」「日の入り 今日 東京」「日の出 計算」が 12 月に立つ。Bing（当サイトの流入の 87%）は
  計算機型のページを素直に拾う（年齢計算・ふるさと納税の実績）

## 作るもの

### 入力

1. **地点**：都道府県のプルダウン（県庁所在地。既定は東京都）／「緯度・経度を入れる」に切り替え（10進の度。北緯・東経の範囲チェック）
   - **位置情報（Geolocation API）は使わない**。`Permissions-Policy: geolocation=()` を CloudFront で出していて（hasokon-infra）、
     使うにはヘッダーを変える必要がある。地点の選択で十分
2. **日付**：既定は今日。ボタン「冬至」「初日の出」「夏至」は**選んでいる日付（既定は今日）から見て次に来る日**を指す（規則で決め、日付を直書きしない）
   - 冬至：選んでいる日付以後で最初の冬至（その日自体が冬至なら、その日）。夏至も同じ
   - 初日の出：選んでいる日付が 1/1 ならその日、それ以外は翌年の 1/1（12/23 に開いた人に、過ぎた冬至・今年の元日を出さない）
   - ボタンのラベルに日付を添える（例「冬至（12/22）」）。冬至・夏至の日付は計算（太陽の視黄経 270°・90° になる日、JST）で出し、
     テストは **2026 年冬至＝12-22・2027 年夏至＝6-21** の固定値で国立天文台の暦要項と一致させる

### 「今日」と時刻の扱い

- 静的エクスポートなので**「今日」はビルド時に決めない**。ブラウザで、**JST の日付**で決める（`Intl.DateTimeFormat('ja-JP', { timeZone: 'Asia/Tokyo' })`
  で年月日を取る。ブラウザのタイムゾーンが JST でない人でも、日本の今日になる）
- 初回の描画（静的 HTML）では日付に依存する値を出さず、**マウント後に今日を決めてから結果を描く**（固定の高さの枠を先に置き、
  ハイドレーションの不一致と日付のちらつき・レイアウトのずれを起こさない）。HTML に焼く既定値は「東京都・初日の出（`HATSUHINODE_YEAR`）」の表だけにする
  （JS が動かないクローラーにも、その年の初日の出の一覧が読める）
- 時刻の表示は**常に JST**。緯度経度の手入力で日本の外の値を入れたときも JST のままで、結果の横に「時刻はすべて日本時間（JST）」と出す。
  手入力の範囲チェックは緯度 −90〜90・経度 −180〜180（日本の外も計算はする）。日本の範囲（緯度 20〜46・経度 122〜154）の外なら
  「日本時間で表示しています。現地時刻ではありません」を出す

### 年の定数（[nenmatagi-2027-rollover.md](./nenmatagi-2027-rollover.md) の教訓）

- 年を持つ定数は **`tools/lib/hinode.ts` の `HATSUHINODE_YEAR = 2027` の1つだけ**。title・description・h1 の補足・FAQ の「2027年の初日の出」・
  HTML に焼く初日の出の一覧は、すべてここから組み立てる（文面に年を直書きしない）
- **上げる日：毎年 11-15**（次の初日の出の 6 週前。「初日の出 2028」の検索が立つ前）に `2028` へ上げる PR を出す。
  1/2〜11/14 の間は title が「初日の出2027」のままだが、その間の「初日の出」の検索は少なく、過ぎた初日の出の時刻を確かめる人もいるので許す。
  上げ忘れを防ぐため、上げる日を nenmatagi の「年の定数の表」（同仕様書の背景 5）に1行足す
- **テストは元日に落ちない**：`new Date().getFullYear()` と `HATSUHINODE_YEAR` を比べる検査は**入れない**。
  定数の値の妥当性は「`HATSUHINODE_YEAR` の 1/1 の東京の日の出が 6:45〜6:55 に入る」のような**日付に依存しない**検査にする。
  （元日の CI はこのツールの山の真っ最中なので、元日に止まる検査を増やさない）

### 結果

1. **日の出・南中・日の入り**（時:分。秒は四捨五入で分に）と**昼の長さ**（○時間○分）、**日の出・日の入りの方位**（度と16方位）
2. 「今日は昨日より昼が ○分 長い／短い」
3. **1か月の表**（日・日の出・日の入り・昼の長さ）。パソコンは表、スマホは日の出・日の入りの2列に畳む
4. **初日の出の一覧**（日付が 12/20〜1/1 のとき、または「初日の出」ボタンで）：47 地点を**早い順**に並べ、
   「最も早いのは ○○（6:xx）・最も遅いのは ○○（7:xx）」を1行で
   - スマホ（390px・320px）では「順位・地点・時刻」の**3列を折り返さない**。初期は**早い5地点・遅い5地点・選んでいる地点**だけを出し、
     「47地点をすべて見る」で開く（47行で結果を押し下げない）
5. 注記（必ず出す）：「**海抜 0m・地平線が見通せる場所**での時刻です。山や建物があると実際に見えるのは数分〜十数分遅れます。
   山頂など高い場所では早くなります」

### 計算のしかた（ページにもそのまま書く）

- 太陽の位置は、ユリウス日から平均近点角・黄経・均時差・赤緯を出す一般的な近似式（Meeus『Astronomical Algorithms』の低精度式。
  米国 NOAA の太陽計算と同じ系統）。誤差は日本の緯度でおおむね 1 分以内
- 日の出・日の入りは**太陽の上辺が地平線に接する**時刻（国立天文台と同じ定義）。地平線での大気差 約35′と太陽の視半径 約16′で、
  中心の高度 −0.8333° として求め、時刻を入れ直して 2〜3 回反復する
- 時刻は日本標準時（UTC+9）。夏時間は無い

起票時に上の式で試算した値（実装時に国立天文台の「各地のこよみ」で突き合わせる。**1分を超えてずれたら式を直す**）：

| 地点（県庁） | 2026-12-22（冬至） | 2027-01-01（初日の出） | 2027-06-21（夏至） |
|---|---|---|---|
| 東京都 | 日の出 6:47・日の入り 16:32 | 日の出 **6:51**・日の入り 16:38 | 日の出 4:26・日の入り 19:00 |
| 北海道（札幌） | 7:03・16:03 | **7:06**・16:10 | 3:55・19:17 |
| 沖縄県（那覇） | 7:13・17:43 | **7:17**・17:48 | 5:38・19:25 |

（緯度経度は国土地理院の県庁の値を使う前提の試算。実装では国土地理院の表から写した値で再計算してテストの期待値にする）

  1. 2027年の初日の出は何時？（47地点の早い・遅い。早い・遅いは東西（経度）だけでなく南北（緯度）でも決まる、を**計算結果の地点名で**書く。起票時に断定しない）
  2. 冬至なのに日の入りが一番早い日ではないのはなぜ？（均時差。日の入りが最も早いのは 12 月上旬、日の出が最も遅いのは 1 月上旬）
  3. 計算の時刻と実際に見える時刻が違うのはなぜ？（地形・建物・標高・雲。海抜0mの計算）
  4. 国立天文台の時刻と違う？（1分以内のずれは丸め。地点の緯度経度の違い）
  5. 位置情報は送られる？（送らない。計算はブラウザの中だけ）
- 出典：国立天文台 暦計算室（定義と検算）・国土地理院（県庁の緯度経度）・国立天文台「暦要項」（冬至・夏至の日付）
- JSON-LD：`WebApplication` と `FAQPage`
