## 提案する仕様

### 入力

1本の入力欄で、形を自動で判定する（`placeholder="192.168.10.0/26"`）。

| 入れたもの | 解釈 |
|---|---|
| `192.168.10.37/26` | アドレス＋プレフィックス長。**ネットワークアドレスに揃えて**範囲を出し、「入力は範囲の中の 38 番目」と添える |
| `192.168.10.0 255.255.255.192` | アドレス＋サブネットマスク（空白・スラッシュ区切りどちらも） |
| `192.168.10.0 0.0.0.63` | ワイルドカードマスク（Cisco の ACL 形式）と判断できればそう扱う（下の「マスクの見分け方」） |
| `255.255.255.192` だけ | マスク⇔プレフィックス長の換算だけ出す |
| `/26` だけ | 同上 |

- 不正なマスク（`255.255.0.255` のように1が連続しない）は「マスクとして使えない形です」と言う

#### マスクとワイルドカードマスクの見分け方（2026-11-24 レビュー指摘で確定）

ドット区切り4つの2番目の値（または単独のマスク）は、次の順で読む。

1. **まずサブネットマスクとして読む**（上位ビットから1が連続し、そのあと0が連続する形）。読めたらサブネットマスクとして扱う
2. サブネットマスクとして読めず、**ワイルドカードマスクとして読める**（上位ビットから0が連続し、そのあと1が連続する形）ならワイルドカードマスクとして扱う
3. どちらでもなければ「マスクとして使えない形です」

**両方に読める2つの値**は、規則1でサブネットマスクとして読み、結果の上に読み方を必ず書く。

| 入力 | 読み方 | 結果の上の一文 |
|---|---|---|
| `0.0.0.0` | /0 のサブネットマスク | 「サブネットマスクとして読みました（/0）。ワイルドカードマスクのつもりなら /32 です」＋ /32 に読み替えるボタン |
| `255.255.255.255` | /32 のサブネットマスク | 「サブネットマスクとして読みました（/32）。ワイルドカードマスクのつもりなら /0 です」＋ /0 に読み替えるボタン |
| `0.0.0.63` | ワイルドカードマスク（規則2） | 「ワイルドカードマスクとして読みました（/26 と同じ範囲）」 |
| `255.255.255.192` | サブネットマスク（規則1） | なし（ふつうの読み方なので書かない） |
- IPv6（`2001:db8::/48`）は**範囲とアドレス数だけ**出す（予約アドレス・分割は IPv4 のみ。下の「やらないこと」）

追加の入力（折りたたみ）：

- **このIPは入るか**：IP を1行1つで貼る → 入る／入らない
- **分割**：新しいプレフィックス長（例 /24 → /26）→ 個数と一覧。**画面に出すのは先頭 64 件**。
  **「全件コピー」は 65,536 件（2^16）まで**。それを超えたら（例：`10.0.0.0/8` を `/30` に分けると 4,194,304 件）個数だけ出し、
  「数が多すぎるので一覧は出しません。先頭と末尾だけ表示します」と言ってコピーのボタンを出さない（スマホのブラウザが固まるのを防ぐ）。
  個数は `/0` → `/32` の 2^32 件まで正しく出す（整数の上限に注意。下のテスト）
- **必要な台数から逆算**：台数と「クラウド」（なし／AWS／Azure／Google Cloud）→ 足りる最小のプレフィックス長。
  「なし」で 1〜2 台のときは **/30（使える2台）を答え**にし、「ルーターどうしの対向リンクだけなら /31（RFC 3021）、1台だけなら /32 も使えます」と注記にとどめる
- **クラウド**の選択は結果の「使える数」にも効く。既定は「なし（従来の −2）」

### 出力（範囲の結果）

| 項目 | 例（`192.168.10.0/26`） |
|---|---|
| ネットワークアドレス | 192.168.10.0 |
| ブロードキャスト | 192.168.10.63 |
| 使える範囲 | 192.168.10.1 〜 192.168.10.62 |
| アドレス数 | 64 |
| 使えるホスト数 | 62（AWS・Azure：59／Google Cloud：60） |
| サブネットマスク | 255.255.255.192 |
| ワイルドカードマスク | 0.0.0.63 |
| 2進数 | ネットワーク部とホスト部を色分け |
| 種類 | プライベート（RFC 1918） |
| 16進数・整数 | `0xC0A80A00`／3232238080（ログや DB の整数表記の確認に） |

- /31 は「2個（RFC 3021 の対向リンク。ブロードキャスト無し）」、/32 は「1個（ホスト1台）」と特別に書く。**−2 を機械的に当てない**
- クラウドを選んだときは、予約される具体的なアドレスを並べる（AWS なら .0 ネットワーク・.1 VPC ルーター・.2 DNS・.3 将来用・.63 ブロードキャスト）
- 各項目にコピーボタン

#### 共有のURLと計測（2026-11-24 レビュー指摘で確定。入力したアドレスを GA4 に送らない）

`tools/lib/analytics.ts` の `trackPageView()` は `page_location: window.location.href` を送るので、**クエリ付きの URL はそのまま GA4 に記録される**（CloudFront のアクセスログにも残る）。
このツールの入力は自社サーバー・自宅回線の**グローバル IP アドレス**になりうるので、次のようにする。

1. **入力のたびに URL を書き換えない。**「共有用のURLをコピー」ボタンを押したときだけ `https://hasokon.com/tools/subnet/?q=…` を組み立ててクリップボードに入れる
2. `?q=` 付きで開かれたときは、値を読んで計算したあと **`history.replaceState` でクエリを消す**
3. **このページの page_view に入力が載らないようにする**：page_view を送る前に `q` を外した URL を `page_location` にする
   （ページ側で渡せるように `trackPageView` に「外すクエリ名」を受ける引数を足すか、このページだけ URL を整えてから送る。どちらにするかは実装 PR で決めてよいが、**`tool_use` の action にもアドレスを入れない**）
4. `tool_use` の action は `calc` / `split` / `reverse` / `contains` と、クラウドを選んだときの `cloud-aws` などだけ（入力値・件数は載せない）


### ロジック（`tools/lib/subnet.ts`。純関数のみ）

- IPv4 は 32 ビットの符号なし整数で扱う（JS のビット演算は符号付き 32 ビットなので `>>> 0` で戻す。**/0 と /32 の境界で落ちやすい**のでテストで押さえる）
- IPv6 は `BigInt` で 128 ビット。`::` の省略形の展開と、RFC 5952 の短縮表記での表示
- クラウドの予約数・プレフィックスの範囲は**定数1か所**に、出典 URL のコメントつきで置く（下の出典）

### テスト（`tools/tests/subnet.test.ts`）

- /0・/8・/24・/26・/30・/31・/32 の範囲と使える数（/31・/32 の特例）
- マスク⇔プレフィックス長の全 33 通りの往復、不正マスクの拒否
- ワイルドカードマスクの判定（`0.0.0.63` は /26 として読む）
- 分割：10.0.0.0/16 → /24 で 256 個、先頭と末尾
- 逆算：50 台・AWS → /26（64−5＝59 ≥ 50）、60 台・AWS → /25（/26 は 59 で足りない）
- 特殊用途の判定（10.0.0.1・172.16.0.1・172.32.0.1（プライベートではない）・100.64.0.1・169.254.1.1・192.0.2.1・8.8.8.8）
- マスクの見分け方：`0.0.0.0` → /0 のマスク（ワイルドカードの読み替え案内つき）、`255.255.255.255` → /32 のマスク（同）、`0.0.0.63` → ワイルドカード（/26）、`255.255.0.255` → 不正
- 分割の上限：`10.0.0.0/8` → `/30` は 4,194,304 件と出し、一覧・全件コピーを出さない。`0.0.0.0/0` → `/32` は 4,294,967,296 件（2^32。32 ビット整数であふれない）。`/16` → `/32` の 65,536 件はコピーできる
- 逆算：「なし」で 1 台・2 台 → /30（/31・/32 は注記）
- 共有：`?q=203.0.113.5/24` で開くと計算結果が出て、URL からクエリが消え、page_view の `page_location` に `203.0.113.5` が入らない
- IPv6：`2001:db8::/32` のアドレス数（2^96）と短縮表記

### やらないこと

- **入力したアドレスの所有者・地域を調べる（WHOIS・GeoIP）。** 外部への送信が要り、「送信なし」の約束が崩れる
- **自分のグローバル IP を表示する。** 同上（サーバーが要る）
- **IPv6 の分割・予約アドレス。** 需要が IPv4 に偏っている。IPv6 は範囲と数だけ
- **ルーティング表・経路集約の最適化（複数ネットワークの最小被覆）。** 1つの CIDR に集約できるかの判定だけなら入れてよいが、後回し
- サブネット設計の「おすすめ」を断定すること（VPC の大きさは組織ごとに違う。一般論の FAQ にとどめる）

## 確認ポイント（テスト環境）

1. `https://test.hasokon.com/tools/subnet/` で `192.168.10.0/26` → 範囲 .1〜.62・62 台、AWS を選ぶと 59 台（テスト環境は Basic 認証）

3. 「必要な台数」に 60・AWS → /25
4. `172.32.0.1` がプライベートと判定されない
5. ネットワークタブで、入力後に外部へのリクエストが出ていない。`?q=203.0.113.5/24` で開いたとき、GA4 の `collect` リクエストの `dl`（page_location）に `203.0.113.5` が入っておらず、アドレスバーからもクエリが消えている

7. `10.0.0.0/8` を `/30` に分割すると個数だけ出て、画面が固まらない
8. 既定の例（`192.168.10.0/26`・逆算の 50 台）のまま開いただけでは `tool_use` が出ない（本番ホストでだけ送るので、本番公開後に GA4 の DebugView で確かめる）
9. **`public` にする前に運営者が GA4 管理画面で確認**：拡張計測の「ブラウザの履歴イベントに基づくページの変更」がオンだと、`history.replaceState` を契機に gtag が page_view を自動で送り、その `page_referrer` に `?q=` 付きの直前の URL が載るおそれがある。オンならこのサイトでは不要なので（page_view は `app/Analytics.tsx` が送る）オフにする（#553 のレビューで指摘）
