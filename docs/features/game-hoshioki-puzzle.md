## 提案する仕様

### ルール

- N×N の盤面が N 個の連結した領域（太枠）に分かれている
- 各行・各列・各領域に星を**ちょうど 1つ**置く（10×10 は 2つ置く「2つ星」も持てるが、初版は 1つ星のみ）
- 星どうしは**斜めを含めて隣接しない**
- 解は 1通り（生成時にソルバーで一意性を保証する）

### サイズと難易度

| モード | 盤面 | 目安 |
|---|---|---|
| かんたん | 5×5 | 1〜2分。導入 |
| ふつう | 7×7 | 3〜5分 |
| むずかしい | 9×9 | 5〜10分 |
| **今日の1問** | 7×7（日付シード） | 全員が同じ問題。クリア時間と連続日数を記録 |

**「今日」は端末のローカル日付**（`new Date()` の年・月・日をそのまま `YYYYMMDD` にする）。
UTC を経由すると日本時間の 0〜9 時に前日の問題が出る。**連続日数の判定も同じローカル日付で行う**
（シードとストリークで日付の取り方が違うと、日付をまたぐ時間帯に記録が壊れる）。

### 操作（games/CLAUDE.md の「画面の約束」どおり。スマホ・PC 両方）

- マスをタップ／クリック：空 → ×（候補消し）→ ★ → 空 の順に切り替え（ナンプレのメモと同じ発想）
- 右クリック／長押し：直接 ★
- 星を置いたとき、同じ行・列・領域と周囲 8マスに**自動で ×** を入れるオプション（既定 ON。解く楽しさを削らない範囲の補助）
- **長押しは iOS の文脈メニュー・テキスト選択と当たる。** マインスイーパと同じ抑止
  （`touch-action` / `user-select` / `contextmenu` の既定動作の停止）を入れる
- 矛盾（同じ行に 2つ、隣接）は赤で示す。**答えは教えない**（ヒント無し）
- 「もどす」「最初から」「チェック（矛盾の有無だけ）」

### 画面

- 盤面は正方形。大きさは **games/CLAUDE.md の「画面の約束」に乗せる**：
  `max-width: min(var(--board-max), max(200px, calc(100dvh - var(--chrome))))`
  （`--chrome` は盤以外が使う高さの実測値、`--board-max` は広い画面での上限）。
  `Game.tsx` から `maxWidth` をインラインで渡さない。目安として、9×9 でも 390px 幅で 1マス 38px 以上になること
- 領域の境界は太線、マスの背景は領域ごとに淡い色分け（色覚に配慮して**線でも区別できる**ようにする）
- クリア画面：かかった時間、今日の1問なら連続日数と「結果をコピー」（`navigator.clipboard`。URL を添える）。
  **コピーする文面に答えを入れない。** 星の位置が分かる絵文字の盤面は、日替わりの答えをそのまま共有することになる。
  入れるのは **日付・サイズ・かかった時間・連続日数**だけ（盤面を絵にしたいときも、星のない領域の色分けまで）
- 記録は `lib/records.ts`（[game-records.md](./game-records.md)）に乗せる。
  **キーはゲームごとに1本**（`hasokon-games:records:hoshioki-puzzle:v1`）で、
  難易度と日替わりは **`variant`**（`easy` / `normal` / `hard` / `daily`）で分ける。
  `records:hoshioki-puzzle:daily` のような別キーは作らない（game-records.md の約束に反する）

#### 連続日数を入れる器：`RecordEntry` を拡張する（案 (a) を採る）

`RecordEntry`（`games/lib/records.ts:32-60`）のフィールドは
`plays` / `wins` / `losses` / `draws` / `bestTimeMs` / `bestScore` / `scoreSum` / `bestMoves` / `clearedIds` で、
**「最終クリア日」と「連続日数」を入れる場所が無い**（`variant` は器の置き場所を分けるだけで、器は増えない）。
2案あるうち、**(a) を採る**：

| 案 | 内容 | 判断 |
|---|---|---|
| **(a)（採用）** | `RecordEntry` に `lastClearedOn?: string`（`'2026-09-18'`）と `streak?: number` を足す | **日替わりはこの先ナンプレ・ノノグラムにも足したくなる仕組み**なので、共有側に置いたほうが結局安い |
| (b) | 既存の `clearedIds?: string[]` に日付を積み、毎回そこから数える | 型は触らずに済むが配列が無限に伸びる。上限の管理が要る |

**(a) を採るので、`game-records.md` の改訂を同じ実装 PR で行う**（全ゲーム共有の型なので、
黙って足すと仕様書と実装がずれる）。**工数に 20k 足した**（下記）。
旧バージョンの記録を読んでも落ちないこと（`streak` が無ければ 0 とみなす）をテストで固定する。

- **localStorage で持つことの弱さを明記しておく。** 端末・ブラウザをまたぐと連続日数は消え、
  プライベートブラウズでは保存されない。「連続◯日」は壊れやすい体験で、
  **静的サイト（サーバー・アカウントを持たない）である以上これは受け入れる**。
  画面でも「この端末のブラウザに保存しています」と添える

### 生成（`games/lib/hoshioki-puzzle.ts`。純関数）

1. 星の配置を先に決める（N クイーン＋隣接禁止の制約をランダム探索で 1つ出す）
2. 各星を種にして領域を成長させ、N 個の連結領域に分割する（成長順をランダムに）
3. バックトラック・ソルバーで解の個数を数え、**1通りでなければ 2 からやり直す**
4. 難易度は「ソルバーが使った推論の段数」で測り、モードごとの範囲に入るまで生成する
4'. **打ち切りは試行回数で決め、壁時計の時間では決めない。** 9×9 は一意解と難易度の条件を
   同時に満たすまで回すので、非力な端末では数秒かかりうる。上限回数を超えたら
   **難易度の条件だけを緩めて返す**（一意解の条件は緩めない）。
   時間で打ち切ると、同じ日付でも端末によって盤面が変わり、日替わりが「全員同じ問題」でなくなる
5. 今日の1問は `seed = YYYYMMDD`（端末のローカル日付）の PRNG（`mulberry32` など）で 1〜4' を決定論的に回す。
   **生成の手順を変えると過去の「今日の1問」が変わるので、`DAILY_GENERATOR_VERSION` を持ち、
   変えたら記録側のキーも変える**

### テスト（`games/tests/hoshioki-puzzle.test.ts`）

- ソルバー：既知の 5×5 問題で解が 1通り。星を 1つ動かした盤面で 0通り
- 生成：全件が一意解・連結領域・領域数 = N。
  **回数は実測して減らした**（この節の約束どおり仕様書に書き戻す）：
  **5×5 を 300 回・7×7 を 200 回・9×9 を 20 回**で、このファイル全体が約2.3秒。
  1,000 回にしなかったのは 9×9 の生成が1面あたり約 200ms かかるため
  （推論の段数を測るのに「置いたら詰む」の読みを全候補ぶん回している）
- 記録の後方互換：`streak` / `lastClearedOn` を持たない既存の記録を読んでも落ちない（`streak` は 0 とみなす）
- 打ち切り：上限回数を 1 にしても一意解の盤面が返る（難易度の条件だけが緩む）
- 日付シード：同じ日付で同じ盤面。`DAILY_GENERATOR_VERSION` を変えると盤面が変わる。
  **同じ日付で 100 回生成して全件同じ盤面**（試行回数での打ち切りが決定論を壊していないこと）
- 記録：`daily` の連続日数が、ローカル日付で 1日空くと 1 に戻り、連日なら増える
- 操作：タップの状態遷移・自動 × の範囲・矛盾検出
- `tests/stage.test.ts` が `robots` の書き忘れを落とす（既存）

## 期待される効果

**検索で新しい枠を取る提案ではない。** 上の「先行するサイトは既にある」のとおり、
日本語・無料・ブラウザの先行（ワウゲーム「毎日スターバトル」ほか）が存在し、名前も造語で検索需要はゼロ。
**効果は次の3つで測る。**

- **再訪（これが主目的）**：今日の1問と連続日数で、`session_start` に対する `first_visit` の比率
  （いま 71%＝`first_visit` 162 / `session_start` 228）が下がるかを見る。
  測り方：GA4 `pagePath = /games/hoshioki-puzzle/` の `activeUsers` に対する `sessions` の比。
  **`public` にならないと測れない**ので、google-index-recovery.md の解除判断が長引けば効果測定も後ろ倒しになる
- **サイト内の回遊**：ロジック系（`tool_use` でブロックパズル 358・マインスイーパ 145・ノノグラム 26）に
  来ている人が、同じサイト内で次の1本に移るか。`/games/` からの遷移で見る
- **日替わり基盤の獲得**：この実装で `records.ts` の型拡張と `games/lib/daily.ts` ができ、
  **ナンプレ・ノノグラム・#236 に日替わりを広げられる**。1本分の工数で他ゲームにも効く

## やらないこと

- **ヒント（次の 1手）。** 純ロジック系は「自力で見つける」が価値。矛盾の表示だけ
- **2つ星モード（10×10 に星 2つ）。** 生成と難易度調整が別物。初版で 1つ星の反応を見てから
- **サーバーでの日替わり配信・ランキング。** 静的サイトの方針に反する。日付シードで代替する
- **他サイトの問題の転記。** 生成器で作る（著作権と、サイトの「コンテンツ＝コード」の型の両方から）
- **猫・動物の絵柄。** Meowdoku の模倣に見える。星で通す
- **連続日数のサーバー保存・アカウント。** 静的サイトの方針に反する。端末をまたぐと消えることは受け入れ、画面に明記する

- **2026-09-19：実装した（`stage: 'wip'`）。** 実装で分かったこと・仕様から動かした点：
  - **でたらめに育てた領域は、まず一意解にならない**（7×7 で 300 回試して 0 件）。
    仕様の「一意でなければ 2 からやり直す」では終わらないので、
    **別解を1つずつ潰す**作りにした（別解が星を置いているマスを隣の領域へ移すと、
    その領域に星が2つ・元の領域に0つとなって別解でなくなり、用意した解はそのまま残る）。
    これで 5×5 が 1ms、7×7 が 4ms、9×9 が約 200ms で出る
  - **難易度は「推論の段数」に、推論の重さを足した点数にした**（`analyze`）。
    使う推論は4段階（候補が1つ／行・列と領域の1対1／複数対応／置いたら詰む）。
    **推論だけで解き切れない盤面は出さない**（当てずっぽうを強いるため）
  - **9×9 は点数の上限を置いていない。** 大きさそのものが難しさなので、
    上を締めると推論で解ける盤面が見つかるまで作り直し続けることになる
  - 盤の実測（390×844）：カードの高さ 644px・9×9 で 1マス 37px。
    **「38px 以上」には 1px 届かない**が、これはカードの左右の余白で決まる値で、
    同じ 9×9 のナンプレ（同条件で 36.9px）と同じ水準。
    盤だけ余白を食い破るより、既存のゲームと揃えるほうを採った
