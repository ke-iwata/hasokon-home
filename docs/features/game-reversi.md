## 提案する仕様

### ゲームの中身

- 盤面 8×8。ルール上の先手は必ず黒（これは変えられない）
- **プレイヤーが黒（先手）か白（後手）かを選べる。既定は黒**
- 置ける場所が無ければ自動でパス。両者パスで終局
- **置ける場所を盤上に薄く表示する**（初心者が最初に詰まるのはここ）
- 石を裏返すアニメーションは 150ms 程度。速すぎると何が起きたか分からない
- 「もどす」対応（既存ゲームと揃える）。**直前の「自分の手番」の局面まで戻す**
- 終局時に石数と勝敗を出す

### 先手・後手を選べるようにする

**初版では「プレイヤーは黒固定」にする案だった。取り下げる。**
理由は、当初の根拠が誤っていたため。

「初手を持てるほうが初心者に易しい」と書いていたが、
**リバーシで先手が有利という事実はない**。むしろ強い相手どうしでは
白（後手）がわずかに有利とされる。黒が先に打つのは慣習であって、
有利不利の話ではない。**固定する理由が無い。**

実装コストもほとんど無い。探索はネガマックスで**すでに手番非依存**に書くので、
CPUが黒を持っても同じ関数がそのまま動く。増えるのは

- 対局開始時の色の選択（既定は黒）
- 白を選んだときに、CPUが黒の初手を先に打つこと
- 選択を `localStorage` に覚えること（強さの選択と同じ扱い）

の3つだけ。

#### 「もどす」の規則を書き直した（**先に見つかったのはこちらの不具合**）

初版は「**1手戻すとCPUの手も含めて2手戻す**」と書いていた。**これは誤り。**
色を選べるようにすると破綻するし、**色を固定していても破綻する。**

- プレイヤーが白のとき、対局の最初はCPUの1手だけが指されている。
  ここで2手戻すと、盤面が初期配置より前に行ってしまう
- **パスが挟まると手数が合わない。** CPUがパスするとCPUの着手は0手なので、
  2手戻すとプレイヤーの手を2つ消してしまう。
  パスはリバーシでは普通に起きるので、これは実際に踏む

正しい規則は手数を数えないもので、色にもパスにも依存しない。

> **「もどす」は、直前の「自分が着手できる手番だった局面」まで戻す。**
> 戻る先が無ければ（対局開始直後なら）ボタンを無効にする。

局面の履歴を積んでおき、後ろから「手番が自分・かつ合法手がある」局面を探すだけで済む。

### CPU の強さ（3段階）

| 段階 | 実装 | 想定 |
|---|---|---|
| かんたん | 合法手からランダム | ルールを覚える段階 |
| ふつう | 評価値つき1手読み（後述の重みテーブル） | 普通に遊ぶ |
| つよい | αβ法で4〜6手読み + 終盤は完全読み切り | 勝てたら嬉しい |

評価は**マス目の重みテーブル**（角が最大、角の斜め隣が大きな負）＋
**着手可能数（mobility）**の合算で足りる。
機械学習も定石データベースも要らない。

**「つよい」の探索は必ず時間で打ち切る**（例：800ms）。
静的書き出しのサイトで、スマホでも動く必要がある。深さで切ると端末差で
フリーズしたように見える。時間で切れば、遅い端末では浅く読むだけで済む。

読みは**Web Worker には出さない**。800ms の打ち切りがあれば UI は詰まらず、
Worker を足すと静的エクスポートのビルド設定が増える。

### CPU の中身

外部ライブラリは使わない。`lib/reversi.ts` に閉じる。

#### 1. 盤面の持ち方

`Int8Array(64)`（0=空 / 1=黒 / -1=白）。ビットボードは使わない
（JSで64bitを扱うと `BigInt` になり、この規模では速くならないうえ読めなくなる）。

**端の折り返しは、方向ごとの残りマス数を先に配ればなくせる。**

```ts
// STEPS[square][dir] = その方向に盤からはみ出さずに進める最大歩数
// 8方向 = [-9, -8, -7, -1, 1, 7, 8, 9]
const STEPS: Int8Array[] = buildSteps(); // モジュール読み込み時に1回だけ作る
```

裏返しの走査は `for (let s = 0; s < STEPS[sq][d]; s++)` で回す。
「1次元配列で `i % 8` の判定を毎回書いて、どこかで書き忘れる」という
**このゲームで一番出やすいバグを、構造で潰す**。

#### 2. 評価関数（`ふつう` と `つよい` が共有する）

3つの合算。係数は定数として1か所にまとめ、テストから参照する。

| 項目 | 内容 | なぜ要るか |
|---|---|---|
| **重みテーブル** | 角 +120 / 角の斜め隣 −40 / 角の隣 −20 / 辺 +10 / その他 ±0 | 角の価値と、角を渡す手の危険を表す |
| **着手可能数（mobility）** | （自分の合法手数 − 相手の合法手数）× 5 | **リバーシで一番効く指標。** 相手の打てる手を減らすと、相手は悪い手を打たされる |
| **確定石** | 角から辺に連続して伸びた、裏返らない石 × 15 | 終盤で効く。重みテーブルだけだと辺を取りすぎて負ける |

**石の数は評価に入れない。** 序盤〜中盤で石を増やすのはむしろ悪手で、
「石を多く取る＝強い」と評価させると初心者より弱いCPUになる。
石数を見るのは終盤の読み切りに入ってからだけ。

#### 3. 探索（`つよい`）

**反復深化 + ネガマックス + αβ枝刈り。**

```
深さ1で読む → 最善手を控える
深さ2で読む → 最善手を控える
深さ3で読む → …
時間切れになったら、その深さは捨てて、直前に完了した深さの手を打つ
```

**打ち切った深さの結果は必ず捨てる。** 途中まで読んだ深さの「最善手」は
一部の手しか評価していないので、平気で悪手が混ざる。
反復深化にするのは、この「いつ止めても直前の完了結果が使える」性質が欲しいため。

**手の並べ替え**（αβの刈り効率はここでほぼ決まる）：
角 → 重みテーブルの降順 → 角の斜め隣を最後。
並べ替えを入れるだけで、同じ時間で1〜2手深く読める。

**終盤の完全読み切り**：空きマスが**10個以下**になったら、
評価関数を使わず**最終石数そのもの**を目的関数にして最後まで読む。
ここは近似ではなく、勝ちが決まるなら確実に勝つ。

#### 4. 時間の打ち切りをテストできる形にする

`performance.now()` を直接呼ぶと、テストが実行環境の速さに依存して落ちる。
`rng` と同じく**注入する**（`lib/cards.ts` の `shuffle(cards, rng)` と同じ約束）。

```ts
export function chooseMove(
  state: ReversiState,
  level: Level,
  opts: {
    /** 思考時間の上限（ms） */
    budgetMs?: number; // 既定 800
    /** 現在時刻。テストでは偽の時計を渡す */
    now?: () => number; // 既定 () => performance.now()
    /** かんたんの手選び・同点の手のばらしに使う */
    rng?: () => number; // 既定 Math.random
  } = {},
): number;
```

これで次の3つがテストで固定できる。

- **`budgetMs: 0` でも必ず合法手を返す**（深さ1だけは必ず完了させる）
- **時計を進めると探索が浅くなる**（打ち切りが効いている）
- **同じ盤面・同じ `rng` なら同じ手を返す**（再現性）

#### 5. 3段階の作り分け

| 段階 | 実装 | 意図 |
|---|---|---|
| かんたん | 合法手から `rng` で1つ選ぶ | 探索なし。**角を避けもしないので初心者が勝てる** |
| ふつう | 深さ1（重みテーブルのみ。mobility と確定石は使わない） | 「目先の良い手」を打つ。角は取るが、角を渡す手も打つ |
| つよい | 反復深化αβ（4〜6手）+ 評価3項目 + 終盤10マス読み切り | 意図して勝ちにいく |

**ふつうは「つよいの探索を浅くしたもの」にしない。**
それだと弱さが「読みの浅さ」としてしか出ず、人間には
「たまに変な手を打つ強いCPU」に見える。
**評価する項目を減らす**と、人間が理解できる負け方（辺を取りすぎる・角を渡す）をする。

### テストで固定すること

- **初期配置**（中央4石）と、黒の初手が**4通り**であること
- **8方向すべて**で正しく裏返ること。**盤の端で折り返さない**こと
  （1次元配列で実装すると端でバグが出やすい。ここは必ず突く）
- **自分の石を飛び越えて裏返さない**こと、**空きマスを挟んでも裏返らない**こと
- 置ける場所が無いとき**パスになる**こと、両者パスで**終局する**こと
- **石が0になった側は即終局**（全滅）すること
- 「つよい」が**角を取れる場面で角を取る**こと、
  **角の斜め隣を序盤に自分から置かない**こと
- CPU の思考が**時間上限内に必ず返る**こと。`now` を注入した偽の時計で、
  **`budgetMs: 0` でも合法手を返す**・**時計を進めると探索が浅くなる**を固定する
- 同じ盤面・同じ `rng` なら**同じ手を返す**こと（`lib/cards.ts` の `seededRng` を使う）
- **石数を評価に入れていない**こと：序盤に「石は多く取れるが角を渡す手」と
  「石は少ないが角を取る手」を並べ、`つよい` が後者を選ぶ
- **プレイヤーが白でも同じ強さで指す**こと：同じ局面を白番・黒番の両方で与え、
  評価が手番非依存（ネガマックス）になっていることを固定する
- **「もどす」がパスをまたいでも壊れない**こと。次の3つを別々に固定する
  1. プレイヤーが白で、CPUの初手だけが指された局面から戻すと**初期配置に戻る**
     （2手戻す実装だと初期配置より前に行こうとして壊れる）
  2. **CPUがパスした直後**に戻すと、プレイヤーの手が**1つだけ**取り消される
     （2手戻す実装だと2つ消える）
  3. 戻る先が無いとき**ボタンが無効**になる

## やらないこと

- **「オセロ」を名前・見出し・meta に使う**。
  登録商標。ノノグラムで「ピクロス」を避けたのと同じ判断。
  検索流入のために他社の商標を使うのは割に合わない

- **オンライン対人戦**。
  静的書き出しのサイトで、サーバーもDBも無い。
  マッチングを入れると構成が根本から変わる

- **定石データベースを持つ**。
  データが重く、公開されている定石集の出どころも確認が要る。
  重みテーブル＋αβで「そこそこ強い」までは十分届く

- **強さを4段階以上にする**。
  「かんたん / ふつう / つよい」で違いが体感できる。
  刻んでも選ぶのが面倒になるだけ

- **Web Worker で読ませる**。
  時間打ち切り（800ms）があれば UI は詰まらない。
  静的エクスポートのビルド設定を増やす理由が無い

- ~~**CPU を先手にする選択肢**。初心者が最初に触るときに不利な側を持たせない~~
  → **撤回した**（2026-08-12）。先手が有利という事実が無いので、
  固定する根拠が無かった。「先手・後手を選べるようにする」に書き直してある

- **手番を対局の途中で入れ替える**。
  リバーシは石の配置と手番が噛み合って進むゲームで、
  途中で入れ替えると局面の意味が壊れる。色を選ぶのは対局開始時だけ
